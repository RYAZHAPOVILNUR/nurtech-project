Модель: [13-data-model-and-permissions.md](../13-data-model-and-permissions.md), разделы «Проект и справочники» (Project, Membership) и «Роли и ключи разрешений».

Из [b00](00-conventions.md): §2–4, §6, §9 (инвариант «минимум один owner»), §11 (удаление участника вызывает эффекты в других пакетах). ## 1. Цель и границы
Дать фронту проекты, членство с ролями и единый механизм проверки прав, на который опираются все следующие пакеты.
- Входит: Project, Membership; управление проектами системным администратором (создание, смена owner — только через `/admin/projects`); список проектов пользователя; участники проекта; `GET /projects/:projectId/me`; общий слой проверки прав (раздел 4); тестовые данные.
- Не входит: статусы, доски, направления, теги (пакет 3), задачи (пакет 4). Поэтому в пакете 2:
  - при создании проекта вызывается шаг «применить шаблон»; его содержимое (статусы, доски, направления шаблонов `dev` и `simple`) описывает [пакет 3](03-dictionaries-and-templates.md), до его готовности шаг ничего не создаёт;
  - удаление участника не снимает его с задач (задач ещё нет); логика подключается в пакете 4.

## 2. Сущности и правила

**Project:** `id`, `key`, `name`, `description?`, `template` (`dev` | `simple`), `createdAt`.
- `key`: `^[A-Z][A-Z0-9]{1,5}$` (2–6 символов, первый — буква), принимается в любом регистре и приводится к верхнему, уникален, после создания не меняется.
- `name`: 1–100 символов; `description`: до 5000 символов, необязательно.
- `template` выбирается при создании и дальше не хранит связи: он только определяет, что создать на старте (пакет 3).

**Membership:** пара (проект, пользователь), `role` (`owner` | `admin` | `member` | `viewer`), `addedAt`; пара уникальна.
- В проекте всегда минимум один owner, на практике один: роль owner назначается только при создании проекта и при смене владельца; через ручки участников её назначить нельзя. Последнего owner нельзя удалить, понизить, деактивировать; при одновременных запросах, из-за которых owner мог бы не остаться, один успешен, а второй получает 409 с кодом ([00, раздел 9](00-conventions.md)).
- В участники попадают только пользователи со статусом `active`. Если участник потом деактивирован, он остаётся в списке (`active = false`), роль у него не меняется, удалить его можно. `active = false` только у деактивированного: участник, которому выдали «Новую ссылку» (статус `invited`), отдаётся с `active = true` и остаётся обычным участником (его можно назначать исполнителем и ревьюером).
- Системный администратор в проекте действует только по своей проектной роли; в проект, где он не участник, у него доступа нет (404, как у любого постороннего). Единственное исключение — ручки `/admin/projects/...` раздела 6: они отдают список проектов и состав участников, но не содержимое.

## 3. Роли и ключи проекта
Состав ключей и матрица «роль → ключ» — только в документе 13, раздел 4 (источник правды по ролям и ключам; перечень ключей сверяется с enum `ProjectPermission` в OpenAPI). Этот раздел фиксирует, как её реализовать.

1. Ответ `/me` и результат проверки в каждой ручке строятся по одной матрице «роль → ключи» документа 13; ручка, для которой у роли нет ключа, отвечает 403.
2. Ключи с пометкой «своё» (`task-archive`, `comment-update`, `comment-delete`, `worklog-update`, `worklog-delete`, `attachment-delete`) отдаются в `/me` у тех ролей, у которых в таблице есть «своё» (viewer получает только `comment-update` и `comment-delete`); принадлежность ресурса проверяется в самой ручке: автор (`authorId`, `userId`, `uploaderId`, для задачи `reporterId`) совпадает с текущим пользователем, либо роль owner/admin (для `comment-update` — только автор).
3. Admin и owner различаются в работе с участниками одним правилом: owner нельзя изменить и удалить никому (раздел 6, Q-23, I-03). Это отдельная проверка в ручках участников, в таблицу ключей она не входит.
4. Тип `ProjectPermission` в OpenAPI перечисляет все ключи проекта, включая те, которые используются только в пакетах 3–8: фронт генерирует тип один раз.

## 4. Порядок ответов в ручках проекта (для всех пакетов)
Проект определяется двумя способами: из пути (`/projects/:projectId/...`, включая поиск задач `.../tasks/search` и задачу по ключу `.../tasks/by-key/:key`) или по ресурсу в пути (`/tasks/:taskId`, `/boards/:boardId`, `/comments/:commentId` и т. п. ведут к проекту ресурса). Проект из query или тела запроса не берётся. Ручки `/admin/...` в этот порядок не входят: у них глобальные ключи, членство не проверяется. Клиент получает ответы в таком порядке:

1. Нет сессии: 401 `unauthenticated`. Флаг `mustChangePassword`: 403 `password_change_required` (правило пакета 1).
2. Проект не найден или пользователь не участник: **404 `not_found`** (существование проекта не раскрывается). Ресурс из чужого проекта тоже 404.
3. Роль не даёт ключ по таблице: 403 `forbidden`.
4. Проверка «своё» и прочие правила ручки (в самой ручке): 403 `forbidden`.

Права вычисляются по текущему членству на каждый запрос: смена роли или удаление из проекта действует на следующем же запросе. Параметр `:projectId` во всех путях — только UUID проекта. Ключ (`PROJ`) в путях API не используется: фронт берёт ключ из адреса страницы `/p/PROJ/...` и находит UUID в уже загруженном `GET /projects` (в элементах есть и `id`, и `key`). Значение не в формате UUID: 404 `not_found`.

## 5. Архивный проект
Архивации проекта в первой версии нет (решено, Q-05, Q-23 I-25: после релиза): ни ручек архивации и возврата, ни статуса и `archivedAt` проекта, ни кода `project_archived`, ни проверки в ручках записи.

## 6. Ручки

Права: `none` — достаточно сессии; ключи — из документа 13. Все пути проектных ручек: `/api/projects/:projectId/...`.

### Администрирование проектов (только системный администратор)
| Ручка | Права | Поведение |
|---|---|---|
| `GET /admin/projects?search=` | `project-list-all` | Все проекты системы без пагинации: `{ items: [{ id, key, name, template, owner: { userId, name, username }, membersCount, createdAt }] }`. `search` по названию и ключу (вхождение, без регистра). Порядок по названию. Содержимое проектов не отдаётся |
| `POST /admin/projects` `{ name, key, template, ownerId, description? }` | `project-create` | Целиком или никак: проект, членство owner для `ownerId`, шаг «применить шаблон» (пакет 3). `ownerId` — активный пользователь: несуществующий — 422 (`fields.ownerId = not_found`), деактивированный — 422 (`fields.ownerId = not_active`). Ключ занят: 409 `project_key_taken`. Формат: 422 с `fields` (`name`, `key`, `template`, `description`). 201 с проектом (как элемент списка выше) |
| `GET /admin/projects/:id/members` | `project-change-owner` | Участники любого проекта для выбора нового owner: `{ items: [Member] }`, формат, порядок и состав (включая деактивированных) как у `GET /projects/:projectId/members`, без `search` и пагинации. Проекта нет (или `:id` не UUID): 404. Системному администратору членство не нужно; содержимое проекта ручка не отдаёт |
| `POST /admin/projects/:id/change-owner` `{ userId }` | `project-change-owner` | Единственный путь смены owner. Новый owner — действующий активный участник проекта, иначе 422 (`fields.userId = not_member` или `not_active`). Уже owner: 409 `already_owner`. Прежний owner становится admin, новый — owner (атомарно). 200 с проектом |

### Проекты пользователя
| Ручка | Права | Поведение |
|---|---|---|
| `GET /projects` | none | Проекты, где текущий пользователь участник: `{ items: [{ id, key, name, role }] }`. Порядок по названию. Без пагинации. Пустой список — фронт показывает экран «Вас ещё не добавили в проекты» |
| `GET /projects/:projectId` | `project-view` | `{ id, key, name, description, template, createdAt }` |
| `GET /projects/:projectId/me` | `project-view` | `{ userId, role, permissions: [ключи проекта] }` по разделу 3. Запрашивается при входе в проект и после любого 403 |
| `PATCH /projects/:projectId` `{ name?, description? }` | `project-update` | Меняет название и описание (пустое описание — `null`). Ключ в теле: 422 (`fields.key = immutable`). 200 с проектом |

### Участники
Элемент списка: `Member = { userId, name, username, role, active }`.

| Ручка | Права | Поведение |
|---|---|---|
| `GET /projects/:projectId/members?search=` | `member-list` | Весь список без пагинации: `{ items: [Member] }`. `search` по имени и логину (вхождение, без регистра) необязателен (фронт ищет сам по загруженному списку). Порядок: owner, admin, member, viewer, внутри роли по имени. В списке и деактивированные |
| `GET /projects/:projectId/member-candidates?search=` | `member-add` | Активные пользователи системы, которых нет в проекте: `{ items: [{ userId, name, username }] }`. `search` обязателен: после `trim` не короче 2 символов (его нет — 422, `fields.search = required`; короче 2 — 422, `fields.search = invalid`); ищет по имени и логину; ответ ограничен 50 записями, порядок по имени. Весь список пользователей системы так не отдаётся, в том числе admin любого проекта. Для admin то же (роль ограничивается при добавлении) |
| `POST /projects/:projectId/members` `{ userIds[], role }` | `member-add` | Добавляет всех сразу или никого. `userIds` — 1–50 уникальных значений, `role` — `admin`, `member` или `viewer`. Роль owner: 422 (`fields.role = invalid`). Admin и owner добавляют любую из трёх ролей. Среди пользователей есть уже участники: 409 `already_member`, `details.userIds`. Есть несуществующие: 422 (`fields.userIds = not_found`); есть деактивированные: 422 (`fields.userIds = not_active`). 201 `{ items: [Member] }` — только добавленные |
| `PATCH /projects/:projectId/members/:userId` `{ role }` | `member-role-change` | `role` — `admin`, `member` или `viewer`. Порядок ответов: цель не участник — 404; цель — вызывающий — 409 `cannot_change_self` (в том числе для owner); цель — owner — 409 `owner_role_locked`; цель деактивирована — 409 `user_deactivated`. Admin и owner меняют роли одинаково (цель любой роли, кроме owner и себя). 200 `{ member: Member }` |
| `DELETE /projects/:projectId/members/:userId` | `member-remove` | Порядок ответов: цель не участник — 404; цель — вызывающий — 409 `cannot_remove_self` (в том числе для owner); цель — owner — 409 `owner_role_locked`. Admin и owner удаляют одинаково. Деактивированного удалить можно. Эффекты (после пакета 4): снимается с исполнителя и ревьюера всех задач проекта, в историю каждой пишется `unassigned_on_member_removal`, подписки (`Watch`) на задачи проекта удаляются; его идентификатор убирается из `assigneeIds` и `reviewerIds` базовых фильтров досок (пакет 3); комментарии, списания времени, история и уже созданные уведомления сохраняются. 204 |

## 7. Связь с пакетом 1
- `GET /admin/users`: `projectsCount` теперь реальный — число проектов, где пользователь участник.
- `POST /admin/users/:id/deactivate`: проверка `last_owner` включается — если пользователь owner хотя бы одного проекта, ответ 409 `last_owner`, `details.projects = [названия]`; сначала нужно передать владение.
- Деактивация и повторная выдача ссылки не удаляют членства.

## 8. Сквозные правила
- Все списки пакета отдаются целиком (пагинации нет), кроме `member-candidates` с лимитом 50.
- Ошибки валидации — единый формат `fields`; новые коды ошибок перечислены в разделе 3 [00-conventions.md](00-conventions.md).

## 9. Тестовые данные (`DEV_SEED=true`)
К данным пакета 1 добавляются (логины фиксированы, пароль у всех из `DEV_SEED_PASSWORD`):
- Пользователи: `anna_owner`, `boris_admin`, `clara_member`, `denis_member`, `eva_viewer`, `fedor_inactive` (деактивирован, но остаётся участником), `gleb_invited` (приглашён, в проектах не состоит), `hanna_free` (активна, в проектах не состоит; нужна для сценария «Вас ещё не добавили»).
- Проект `DEMO` (шаблон `dev`): `anna_owner` — owner, `boris_admin` — admin, `clara_member` и `denis_member` — member, `eva_viewer` — viewer, `fedor_inactive` — member.
- Проект `SIMPLE` (шаблон `simple`): `boris_admin` — owner, `clara_member` — member.
- Системный администратор из пакета 1 в проектах не состоит.
Содержимое проектов (статусы, доски, задачи) добавляют пакеты 3 и 4.

## 10. Критерии приёмки
1. Системный администратор создаёт проект: ключ приводится к верхнему регистру, повторный ключ даёт 409 `project_key_taken`, некорректный — 422; `ownerId` получает роль owner; проект сразу виден владельцу в `GET /projects`.
2. `GET /projects` у `hanna_free` пустой; у `anna_owner` содержит `DEMO` (role = owner).
3. Посторонний (в том числе системный администратор, не состоящий в проекте) получает 404 на `GET /projects/<uuid DEMO>`, `/me` и `/members`; запрос с ключом вместо UUID даёт 404.
4. `GET /projects/<uuid DEMO>/me` возвращает роль и набор ключей строго по таблице документа 13 для каждой из четырёх ролей (у viewer — только ключи чтения и «своё» по комментариям).
6. `boris_admin` в `DEMO` может добавить участника с любой из ролей admin, member, viewer, менять роли и удалять любых участников, кроме owner и себя; изменить или удалить `anna_owner` нельзя (409 `owner_role_locked`). Порядок ответов: цель не участник — 404, затем сам себя — 409 `cannot_change_self`/`cannot_remove_self`, затем цель owner — 409 `owner_role_locked`.
7. `anna_owner` не может изменить свою роль (409 `cannot_change_self`) и удалить себя (409 `cannot_remove_self`); эти коды она получает вместо `owner_role_locked`.
8. Добавление нескольких человек одним запросом атомарно: при одном уже состоящем в проекте не добавляется никто, `details.userIds` указывает на него.
9. Смена владельца (`change-owner`) делает прежнего owner admin, в проекте остаётся один owner. Пути `POST /projects/:projectId/transfer-owner`, `/archive`, `/restore` отсутствуют (404). `GET /admin/projects/<uuid DEMO>/members` у системного администратора, не состоящего в проекте, отдаёт всех шестерых участников `DEMO` (включая `fedor_inactive` с `active = false`), без ключа `project-change-owner` — 403; несуществующий проект — 404.
10. Деактивация владельца проекта даёт 409 `last_owner` со списком названий; после передачи владения деактивация проходит; `projectsCount` в списке пользователей соответствует числу проектов.
11. `member-candidates` не возвращает неактивных, приглашённых и уже участников; не более 50 записей; поиск по имени и логину; без `search` — 422 (`fields.search = required`), с одним значимым символом (пробелы по краям не считаются) — 422 (`fields.search = invalid`), с двумя — 200; admin любого проекта не получает весь список без `search`.
12. Для каждой проектной ручки и каждой из четырёх ролей ответ соответствует матрице документа 13 (без ключа — 403, не участник — 404); в OpenAPI у каждой ручки есть `x-permission`; тип `ProjectPermission` содержит все ключи документа 13.
13. `GET /admin/projects` отдаёт все проекты системы: `search` ищет по названию и ключу без учёта регистра, `membersCount` верен, порядок по названию; без ключа `project-list-all` — 403.
14. `GET /projects/<uuid>` участнику отдаёт данные проекта; `PATCH` меняет название и описание (пустое описание хранится как `null`); ключ в теле — 422 (`fields.key = immutable`).
16. Одновременные запросы (по [00, раздел 9](00-conventions.md)): два одновременных `change-owner` для одного проекта с разными новыми owner — один успешен, второй не проходит с кодом (`already_owner` или `validation_failed`), owner в проекте ровно один; одновременное удаление и понижение единственного owner не оставляют проект без owner.
17. После `POST /admin/users/:id/reissue` для `clara_member` запрос `GET /projects/<uuid DEMO>/members` отдаёт её с `active = true`, и её можно назначить исполнителем задачи (`PATCH /tasks/:taskId`, `assigneeId`); деактивированный `fedor_inactive` отдаётся с `active = false`.

## 11. Открытые вопросы
Открытых вопросов нет. Решено: `projectsCount` и проверка `last_owner` учитывают все проекты пользователя, архивации проекта нет (раздел 7); в путях API проект задаётся только UUID.

## 12. Рекомендации (необязательно)
- **Права.** Держать одну константу «роль → набор ключей», по ней строить и `/me`, и проверки; в маршрутах объявлять нужный ключ декоратором или метаданными (например `@RequirePermission('task-update')`) и проверять единым guard в порядке: сессия → `mustChangePassword` → членство → ключ → правила ручки.
- **Owner.** Проверку «останется хотя бы один owner» выполнять в одной транзакции под блокировкой строки проекта (`SELECT … FOR UPDATE`) — [00, раздел 13](00-conventions.md).
- **Хранение.** Уникальный ключ проекта и пара (проект, пользователь), счётчик номеров задач проекта; индексы и внешние ключи — [13](../13-data-model-and-permissions.md), раздел 7.
