## 1. Цель и границы
Показать пользователю, что произошло с задачами, на которые он назначен или подписан, в приложении (колокольчик, список) и в Telegram.
- Входит: Notification; формирование уведомлений из событий задач; ручки колокольчика; очередь и отправка сообщений в Telegram; очистка старых данных; тестовые данные.
- Не входит: настройки типов уведомлений (их нет, кроме переключателя Telegram в профиле, пакет 1), почта, SSE и push (SSE — после релиза, Q-05; требования безопасности при возврате — C-17 в [01](../01-scope.md)).

## 2. События и получатели

**Когда создаются уведомления.** Уведомления создаются после успешного завершения действия пользователя; сбой при их формировании или отправке никогда не меняет ответ самого действия (клиент получает обычный успех).

| Действие (запрос пользователя) | Откуда |
|---|---|
| Назначен, сменён или снят исполнитель | создание задачи с исполнителем; `PATCH` с новым `assigneeId` (в том числе `null`) |
| Назначен, сменён или снят ревьюер | создание задачи с ревьюером; `PATCH` с новым `reviewerId` (в том числе `null`) |
| Сменён статус | `move` со сменой статуса (причина, если была, попадает в уведомление) |
| Новый комментарий | `POST .../comments` (только `kind = comment`) |
| Новые упоминания | `PATCH /comments/:id`, добавивший упоминания (участвуют только новые упомянутые) |

Действия, не порождающие уведомлений: массовые системные операции (удаление статуса, направления или тега с переносом, снятие удалённого участника с задач, каскадная архивация), правки полей кроме исполнителя и ревьюера (в том числе приоритета и срока), подписка и отписка, списание времени, ссылки и связи, архивация, комментарии-причины (`status_reason`: их заменяет уведомление о смене статуса, причина передаётся в `details`).

**Правила получателей** (на одно действие). Одно действие — один запрос пользователя: создание задачи, правка полей, перенос карточки, отправка или правка комментария.
1. Автор действия о своём действии не уведомляется.
2. Получатель — активный пользователь и текущий участник проекта задачи.
3. На одно действие каждому получателю — не больше одного уведомления: если человеку положено несколько, остаётся одно по приоритету типов `mentioned` > `assigned` / `reviewer_assigned` > `commented` / `status_changed` / `assignee_changed` / `reviewer_changed` (при равном приоритете — по порядку перечисления). При создании задачи `assignee_changed` и `reviewer_changed` не создаются никому.

| Тип | Кому | Когда |
|---|---|---|
| `assigned` | новый исполнитель | назначен исполнителем (в том числе при создании задачи) |
| `reviewer_assigned` | новый ревьюер | назначен ревьюером |
| `mentioned` | каждый упомянутый | упомянут в новом комментарии или добавлен упоминанием при правке |
| `commented` | все подписчики задачи (`Watch`), кроме автора и упомянутых в этом комментарии | новый комментарий `kind = comment` |
| `status_changed` | все подписчики, кроме автора | статус изменился |
| `assignee_changed` | все подписчики, кроме автора и нового исполнителя | исполнитель сменился или снят |
| `reviewer_changed` | все подписчики, кроме автора и нового ревьюера | ревьюер сменился или снят (при создании задачи не создаётся) |
Подписчики определяются на момент события, **после** автоподписок этого действия (пакет 7): новый исполнитель и автор комментария уже подписаны, но получают только свои типы по правилу 3.

**Снятие исполнителя или ревьюера** (`null`): получателя нет, поэтому `assigned` и `reviewer_assigned` не создаются. Подписчики (кроме автора) получают `assignee_changed` или `reviewer_changed` с `to = null`.

**`details`** по типам:
- `status_changed`: `{ from: { id, label }, to: { id, label }, reason? }`; `reason` — текст причины, если она передана.
- `assignee_changed` и `reviewer_changed`: `{ from: { id, label } | null, to: { id, label } | null }` (`label` — имя пользователя; `null` — не назначен).
- `commented`, `mentioned`: `{ commentId, excerpt }`; `excerpt` — первые 200 символов текста комментария как есть (markdown не рендерится).
- `assigned`, `reviewer_assigned`: все поля `details` равны `null`.
- В ответе API `details` всегда объект `NotificationDetails` с пятью полями (`from`, `to`, `reason`, `commentId`, `excerpt`); поля, не относящиеся к типу, равны `null`.

## 3. Сущности

**Notification:** `id`, получатель, `type`, `actor`, `task`, `details`, `createdAt`, `read` — как в `NotificationItem` (раздел 4).
- Уведомление остаётся после удаления комментария (`commentId` в `details` тогда ведёт в никуда, а `excerpt` остаётся); задачи не удаляются.
- В списке и счётчике показываются только уведомления по задачам проектов, в которых пользователь **сейчас** участник (удалённый из проекта их не видит; при возврате они снова видны).

## 4. Ручки
Права: ключей нет (личное действие, достаточно сессии).

| Ручка | Поведение |
|---|---|
| `GET /notifications?limit=&before=` | Курсорная выдача: `{ items: [NotificationItem], hasMore, nextCursor }`, от новых к старым (в отличие от комментариев). `limit` 1–50, по умолчанию 20. `before` — `nextCursor` предыдущего ответа (курсор последнего показанного уведомления, `null`, если `hasMore = false`); строка, которая не разбирается: 422 (`fields.before = "invalid"`). Порядок и курсор — по паре (`createdAt`, `id`), устройство курсора — [00, раздел 12](00-conventions.md): удалённое (в том числе очисткой старше 90 дней) уведомление-курсор не ломает выдачу. Только собственные уведомления |
| `GET /notifications/unread-count` | `{ count }` — число непрочитанных (точное; «99+» формирует фронт) |
| `POST /notifications/:notificationId/read` | Помечает прочитанным; уже прочитанное — успех без изменений. Чужое или несуществующее: 404. 204 |
| `POST /notifications/read-all` | Помечает прочитанными все непрочитанные текущего пользователя. 204 |

`NotificationItem`: `{ id, type, actor: UserRef, task: { id, key, title, projectId, projectKey }, details, createdAt, read }` (`read` — булево, `readAt` наружу не отдаётся).

Счётчик опрашивается раз в 30 секунд на пользователя, поэтому `unread-count` должен отвечать быстро (ориентир — единицы миллисекунд на сидовых данных).

## 5. Отправка в Telegram

**Условие.** Для каждого созданного уведомления сообщение ставится в очередь, если у получателя `notifyTelegram = true`, Telegram привязан и бот включён (задан `TELEGRAM_BOT_TOKEN`). Если бот не настроен, сообщения не отправляются, а ручки приложения работают как обычно.

**Текст.** HTML-разметка Telegram (`parse_mode = HTML`), все подставляемые значения экранируются (`&`, `<`, `>`). Шаблоны (русский язык):
| Тип | Текст |
|---|---|
| `assigned` | `Вас назначили исполнителем · {Имя}` |
| `reviewer_assigned` | `Вас назначили ревьюером · {Имя}` |
| `mentioned` | `Вас упомянули в комментарии · {Имя}` + строка с отрывком |
| `commented` | `Новый комментарий · {Имя}` + строка с отрывком |
| `status_changed` | `Статус изменён: {из} → {в} · {Имя}` + при наличии «Причина: …» (до 300 символов) |
| `assignee_changed` | `Исполнитель изменён: {из} → {в} · {Имя}` (пусто: «не назначен») |
| `reviewer_changed` | `Ревьюер изменён: {из} → {в} · {Имя}` (пусто: «не назначен») |
`{Имя}` и имена в «из» / «в» — `User.name` целиком; «Иван П.» в примерах документа 11 — условность записи. Каждое сообщение содержит строку `PROJ-123 Название задачи` и ссылку `APP_BASE_URL/p/PROJ/tasks/PROJ-123`. Сообщение не длиннее 4096 символов (Telegram), отрывки при необходимости усекаются. Тексты в нейтральной форме без рода глагола (Q-22): автор действия указывается в конце после « · ». Те же формулировки показывает приложение ([11](../11-navigation-and-notifications.md), раздел 6).

**Очередь и повторы.** Сообщения уходят в Telegram в фоне, в течение нескольких секунд после действия; несколько экземпляров приложения не отправляют одно сообщение дважды.
- **Проверка перед отправкой.** Для каждого сообщения заново проверяется: пользователь активен, `notifyTelegram = true`, привязанный `telegramId` тот же, что при постановке в очередь, пользователь по-прежнему участник проекта задачи. Если хотя бы одно не выполнено, сообщение не отправляется и пропадает.
- **Снятие очереди.** При отвязке Telegram, выдаче новой ссылки (`reissue`) и деактивации пользователя все его неотправленные сообщения пропадают.
- Временная ошибка (сеть, 5xx, 429): повторы через 1 минуту, 5 минут, 30 минут, 2 часа; после 5 неудач сообщение не отправляется. На 429 используется `retry_after` из ответа Telegram.
- Окончательная ошибка (чат не найден, пользователь заблокировал бота — коды 400/403): повторов нет, у пользователя `notifyTelegram` выключается (`GET /auth/me` отдаёт `false`). В приложении включить снова можно в профиле.
- Скорость: не более 20 сообщений в секунду всего и одного сообщения в секунду на чат.
- Порядок для одного получателя сохраняется (по времени создания уведомлений).

**Webhook.** Если `TELEGRAM_MODE = webhook`, бот принимает обновления на `POST /telegram/webhook`: публичная ручка, секрет проверяется по заголовку `X-Telegram-Bot-Api-Secret-Token` (значение `TELEGRAM_WEBHOOK_SECRET`, он же передаётся в `setWebhook` как `secret_token`), при несовпадении 403. В режиме `webhook` с пустым `TELEGRAM_WEBHOOK_SECRET` приложение отказывается стартовать; в режиме `polling` ручка выключена (404). Тело — объект Update Telegram (обрабатываются только команды `/start <token>` и нажатия кнопок подтверждения `callback_query` пакета 1 из личных чатов, `chat.type = private`; обновления из групп и каналов игнорируются; в `setWebhook` передаётся `allowed_updates = ["message", "callback_query"]`). Всегда отвечает 200 на корректный запрос, чтобы Telegram не повторял доставку.

## 6. Очистка
Ежедневно удаляются уведомления старше 90 дней (прочитанные и нет); в списке и счётчике их больше нет.

## 9. Критерии приёмки
1. Назначение исполнителя создаёт `assigned` новому исполнителю и `assignee_changed` остальным подписчикам (кроме автора); сам себя назначивший ничего не получает. Снятие исполнителя (`assigneeId = null`) не создаёт `assigned`, подписчики получают `assignee_changed` с `to = null`.
2. Смена статуса через `move` создаёт `status_changed` всем подписчикам кроме автора, в `details` старый и новый статус и причина (если была); перестановка внутри колонки уведомлений не создаёт.
3. Комментарий создаёт `commented` подписчикам (кроме автора и упомянутых) и `mentioned` упомянутым; один человек получает по одному комментарию не более одного уведомления; правка с добавлением упоминания уведомляет только вновь упомянутых; обычная правка текста уведомлений не создаёт.
4. Массовые операции (удаление статуса с переносом, снятие участника с задач) и каскадная архивация уведомлений не создают.
5. Деактивированные пользователи и пользователи, не состоящие в проекте, уведомлений не получают; удалённый из проекта не видит старых уведомлений проекта в списке и счётчике.
6. `GET /notifications`: порядок от новых к старым, `limit` и `before` (= `nextCursor` предыдущего ответа) работают без пропусков и повторов, в том числе когда уведомление-курсор уже удалено, `hasMore` верен; чужие уведомления не отдаются; `unread-count` совпадает с числом непрочитанных; `POST .../read` и `read-all` уменьшают счётчик; чужое уведомление — 404.
7. Если `notifyTelegram` включён и Telegram привязан, каждое уведомление порождает сообщение с корректным текстом и ссылкой; HTML в названиях и текстах экранируется (проверяется с подменённым Telegram API или на стенде с ботом — способ на усмотрение разработчика).
8. Временная ошибка Telegram повторяется через 1 / 5 / 30 минут и 2 часа и после 5 неудач больше не повторяется; ошибка «пользователь заблокировал бота» выключает `notifyTelegram` (`GET /auth/me` отдаёт `false`) и не повторяется (проверяется на стенде с подменёнными ответами Telegram; способ и сжатие времени — на усмотрение разработчика).
9. Недоступность Telegram или сбой при формировании уведомлений не приводит к ошибке в ручках комментариев, переносов и правок: они отвечают как обычно.
10. Webhook: запрос без верного секрета — 403; с верным и командой `/start <token>` или `callback_query` кнопки подтверждения работает как в пакете 1; update из группового чата игнорируется (200, действий нет); в режиме `polling` ручка отвечает 404; в режиме `webhook` с пустым секретом приложение не стартует.
11. Уведомления старше 90 дней не отдаются в `GET /notifications` и не входят в `unread-count` (проверяется на подготовленных данных).
12. Перед отправкой сообщения проверяются условия: после отвязки Telegram, после деактивации, после удаления из проекта, при `notifyTelegram = false` и при смене привязанного Telegram сообщение не уходит.
13. Отвязка Telegram, новая ссылка и деактивация отменяют все неотправленные сообщения пользователя.
14. Два экземпляра приложения против одного хранилища не отправляют одно сообщение дважды.
15. В OpenAPI у ручек указан `x-permission: none`, у webhook — `x-public`; `NotificationType` содержит `reviewer_changed`; `details` — всегда объект.
16. Смена ревьюера: подписчикам задачи (кроме автора действия и нового ревьюера) приходит одно `reviewer_changed` с `from` и `to`; новому ревьюеру — `reviewer_assigned`, а не `reviewer_changed`; снятие ревьюера — `reviewer_changed` с `to = null` подписчикам (кроме автора), получателя `reviewer_assigned` нет; при создании задачи `reviewer_changed` и `assignee_changed` не создаются никому. Смена приоритета, срока и других полей уведомлений не создаёт.
17. Одно действие — одно уведомление: Анна создаёт задачу с исполнителем Иваном и ревьюером Марией — Иван получает одно `assigned`, Мария — одно `reviewer_assigned`, Анна — ничего; Иван, назначенный и исполнителем, и ревьюером, получает одно уведомление (`assigned`); подписчик, упомянутый в комментарии, получает `mentioned`, а не `commented`.

## 10. Открытые вопросы
1. **Решено:** уведомления хранятся 90 дней, затем удаляются (раздел 6; на странице — [11-navigation-and-notifications.md](../11-navigation-and-notifications.md), «Панель»).
2. **Решено (Q-33 б):** подписчики получают `reviewer_changed` при смене и снятии ревьюера (раздел 2); при создании задачи тип не создаётся.
3. **Решено (Q-22):** пола в профиле нет, поэтому в Telegram и в приложении нейтральная форма с автором в конце («Вас назначили исполнителем · Иван П.»).
4. **Решено:** смена приоритета, срока и других полей уведомлений не вызывает — не уведомляем.

## 11. Рекомендации (необязательно)
- **Источник событий.** Сервисы пакетов 4, 6, 7 публикуют внутренние доменные события (`TaskAssigned`, `TaskReviewerAssigned`, `TaskStatusChanged`, `CommentCreated`, `CommentMentionsAdded`) после коммита, модуль уведомлений подписан на них; ошибки модуля пишутся в лог. События одного запроса публиковать пачкой (например `publishDomainEvents([...], { actorId, requestId })`), чтобы правила получателей применялись ко всей пачке (один человек — одно уведомление). Потерю уведомлений при падении процесса между коммитом и обработкой можно принять; отдельную таблицу исходящих событий не вводить.
- **Хранение уведомлений.** Индексы `(userId, createdAt desc, id)` и частичный `(userId) where readAt is null`; `commentId` в `details` — не внешний ключ ([13](../13-data-model-and-permissions.md), раздел 7).
- **Очередь Telegram (`TelegramOutbox`).** Поля: `id`, `userId`, `projectId` (проект задачи, для проверки членства), `chatId` (Telegram ID на момент постановки), `text`, `status` (`pending` | `sent` | `failed`), `attempts`, `nextAttemptAt`, `lastError?`, `createdAt`, `sentAt?`; индекс `(status, nextAttemptAt)`. Обработчик раз в 5 секунд берёт записи `pending` с `nextAttemptAt <= now()` выборкой `FOR UPDATE SKIP LOCKED` (несколько экземпляров не отправят одну запись дважды). Очистка: `sent` старше 7 дней и `failed` старше 30 дней.
- **Webhook.** Секреты сравнивать за постоянное время (`timingSafeEqual`).
- **Тестовые данные.** В `DEMO` у `anna_owner` и `clara_member` уведомления всех семи типов (в том числе одно `reviewer_changed`); не меньше 30 у одного из них (проверка «Показать ещё» и курсора); часть прочитана, часть нет.
- **Отладка без бота.** `TELEGRAM_DRY_RUN=true`: сообщения не отправляются, а пишутся в журнал приложения; в этом режиме удобно проверять текст и экранирование HTML и то, что два экземпляра пишут по одной записи на сообщение.
- **Тесты.** Мок Telegram API, управляемые часы для расписания повторов, подмена обработчика событий на выбрасывающий исключение — на усмотрение разработчика.
