## 1. Цель и границы
Дать фронту задачи: создание (в том числе подзадач), чтение, правку полей, теги, архивацию и восстановление, список подзадач и историю изменений. На этом пакете строятся все следующие.
- Входит: Task, TaskTag, HistoryEvent; нумерация задач проекта; ручки раздела 5; запись истории при любых изменениях задачи; подключение заготовок пакетов 2 и 3 (раздел 7); тестовые данные.
- Не входит (и поэтому в ответах пока заглушки):
  - связи, ссылки и поле `blocked` (пакет 5); список «Все задачи» и поиск (пакет 5);
  - смена статуса, порядок карточек, доски (пакет 6): статус меняется только ручкой переноса `move`; `PATCH` статус не принимает;
  - комментарии и списания времени (пакет 7): `spentMinutes` пока всегда 0, суммы по подзадачам по времени тоже 0;
  - подписки, уведомления, бот (пакеты 7–8).

## 2. Сущности и правила

**Task:** `id`, `projectId`, `number`, `parentId?`, `type` (`task` | `bug` | `subtask`), `title`, `description?`, `statusId`, `priority` (`low` | `medium` | `high` | `critical`), `assigneeId?`, `reviewerId?`, `subsystemId?`, `dueDate?`, `estimateMinutes?`, `reporterId`, `rank`, `createdAt`, `updatedAt`, `resolvedAt?`, `archivedAt?`.

- **Ключ** `KEY-number`, например `PROJ-152`; у всех типов (подзадача тоже) общая нумерация проекта. Номер уникален в проекте и идёт по возрастанию без повторов; два одновременных создания получают разные номера. Номера не переиспользуются. Сид и скрипты генерации задач тоже не нарушают уникальность номеров.
- **Название:** после `trim` 1–100 символов. **Описание:** markdown, до 5000 символов, необязательно (пустая строка хранится как `null`). Разметку бэкенд не очищает и не рендерит: очистка HTML — на фронте.
- **Тип:** Task и Bug меняются друг на друга (`PATCH`), Subtask фиксирован; сделать Subtask из Task или Task из Subtask нельзя.
- **Родитель:** `parentId` только у Subtask, обязателен при создании, ссылается на Task или Bug того же проекта, не архивный; после создания не меняется. Подзадача у подзадачи невозможна. Подзадачи у архивного родителя не остаётся и при одновременных запросах «создать подзадачу» и «архивировать родителя» ([00, раздел 9](00-conventions.md)).
- **Приоритет:** по умолчанию `medium`.
- **Исполнитель и ревьюер:** участники этого проекта. Новое назначение разрешено только не деактивированному участнику (роль любая, кроме ограничений ключей; участник со статусом `invited` после «Новой ссылки» назначается); если человек потом деактивирован, он остаётся в задаче и отдаётся с `active = false`. Исполнитель и ревьюер могут совпадать.
- **Срок** `dueDate`: дата `YYYY-MM-DD`, любая (прошедшая тоже). **Оценка** `estimateMinutes`: целое от 1 до 100000 (≈ 1666 часов), `null` — не задана.
- **Теги:** до 50 на задачу, только теги этого проекта.
- **Статус:** при создании — переданный или первый по `position` статус без `requiresReason` (если такого нет — 422, `fields.statusId = "required"`); в переданный статус с `requiresReason` создавать нельзя (причину некуда записать): 422 (`fields.statusId = "reason_required"`). Исключение — системный перенос задач при удалении статуса, причина там не нужна ([03, раздел 3](03-dictionaries-and-templates.md)). Дальше статус меняет пакет 6.
- **`resolvedAt`:** ставится, когда задача оказывается в статусе категории `done`, и сбрасывается при выходе из `done`. Задним числом при смене категории самого статуса не пересчитывается. Одинаково для переноса карточки ([пакет 6](06-boards-and-move.md)) и для переноса задач при удалении статуса ([пакет 3](03-dictionaries-and-templates.md)).
- **Порядок карточек.** Внутри статуса карточки идут в порядке, который задаёт пакет 6 ([06-boards-and-move.md](06-boards-and-move.md), раздел 3); наружу порядок отдаётся как `rank` — непрозрачная строка, клиент её не разбирает, а сортирует по возрастанию. Новая задача встаёт в конец колонки своего статуса (после всех задач статуса, включая архивные).
- **`updatedAt`:** обновляется при любом изменении данных задачи: поля, теги, статус, исполнитель, архивация и восстановление, связи и ссылки (пакет 5), а также добавление, правка и удаление комментария (пакет 7). Списания времени `updatedAt` не меняют. Правка, не меняющая значение (то же значение, что уже сохранено), ничего не пишет: ни в историю, ни в `updatedAt`.
- **Параллельные правки:** `PATCH` частичный, побеждает последнее сохранение на уровне поля; версий и блокировок нет.

**HistoryEvent:** `id`, `taskId`, `actorId`, `kind`, `field?`, `oldValue?`, `newValue?`, `createdAt`.
- `kind`: `created`, `field_changed`, `link_added`, `link_removed`, `url_added`, `url_removed`, `tag_added`, `tag_removed`, `archived`, `restored`, `unassigned_on_member_removal`.
- Для `field_changed` поле `field` — одно из `status`, `assignee`, `reviewer`, `priority`, `type`, `subsystem`, `dueDate`, `estimateMinutes`, `parent` (резерв: родитель после создания не меняется, событие не пишется). Название и описание, комментарии и списания времени в историю не пишутся.
- Значение (`oldValue`, `newValue`) — объект `{ id, label }` или `null`. Для ссылок на сущности (`status`, `assignee`, `reviewer`, `subsystem`, `parent`, тег, связанная задача) `id` — идентификатор, `label` — название на момент события (имя, название, ключ), чтобы переименование и удаление не ломали историю. Для скаляров (`priority`, `type`, `dueDate`, `estimateMinutes`) `id = null`, `label` — «сырое» значение (`high`, `bug`, `2026-11-03`, `150`); форматирует фронт.
- Значения по видам событий:

| `kind` | `field` | `oldValue` | `newValue` |
|---|---|---|---|
| `created`, `archived`, `restored` | `null` | `null` | `null` |
| `field_changed` | поле (`status`, `assignee`, …) | прежнее значение | новое значение |
| `tag_added` | `null` | `null` | `{ id, label }` тега |
| `tag_removed` | `null` | `{ id, label }` тега | `null` |
| `link_added`, `link_removed` | тип связи с точки зрения этой задачи | `null` или `{ id, label }` другой задачи (при удалении) | `{ id, label }` другой задачи (при добавлении) или `null` |
| `url_added`, `url_removed` | `null` | `null` или `{ id, label }` ссылки (при удалении) | `{ id, label }` ссылки (при добавлении) или `null` |
| `unassigned_on_member_removal` | `assignee` или `reviewer` | снятый пользователь `{ id, label }` | `null` |
- За один запрос с несколькими изменёнными полями пишется по событию на каждое поле с одним и тем же `createdAt`. История неизменяема; события не удаляются, даже когда удалён пользователь или справочник.

## 3. Права
Проверки — общим слоем (пакет 2, раздел 4). Ключи: `task-view`, `task-create`, `task-update`, `task-archive` (своё: `reporterId`; admin и owner — любую), `task-restore`. Теги в `PATCH` и при создании требуют только `task-update` / `task-create`; новый тег создаётся отдельной ручкой пакета 3 (`tag-create`).
Архивная задача: любые изменения, кроме восстановления, — 409 `task_archived`. Читать её по ключу могут все роли проекта (карточка показывает баннер), в списках и на досках архивные задачи не появляются (пакеты 5–6).

## 4. Форматы ответов
- **`TaskSummary`** (строки списков и подзадач): `id`, `key`, `type`, `title`, `status` `{ id, name, color, category }`, `priority`, `assignee` `UserRef | null`, `dueDate`, `isOverdue`, `subsystem` `{ id, name } | null`, `tags` `[{ id, name }]`, `estimateMinutes`, `spentMinutes`, `updatedAt`, `subtaskCount`, `parent` `{ id, key, title } | null`, `archived` (булево).
- **`TaskDetail`**: все поля `TaskSummary` плюс `projectId`, `description`, `reviewer` `UserRef | null`, `reporter` `UserRef`, `commentCount` (число комментариев задачи, считает пакет 7; до пакета 7 — 0), `subtasksDone`, `subtasksEstimateMinutes`, `subtasksSpentMinutes`, `createdAt`, `resolvedAt`, `archivedAt`. Пакет 5 добавляет `links`, `urls`, `blocked`; пакет 7 — `watching`.
- **`UserRef`** = `{ userId, name, username, active }`.
- `isOverdue` = срок задан, он раньше сегодняшней даты UTC и категория статуса не `done`; для архивных задач `false`.
- `subtaskCount`, `subtasksDone`, `subtasksEstimateMinutes`, `subtasksSpentMinutes` считаются только по неархивным подзадачам; «закрыта» — статус категории `done`. Суммы не включают собственные значения родителя. Для задач без подзадач — нули.

## 5. Ручки

| Ручка | Права | Поведение |
|---|---|---|
| `POST /projects/:projectId/tasks` `{ type, title, description?, statusId?, priority?, assigneeId?, reviewerId?, subsystemId?, dueDate?, estimateMinutes?, tagIds?, parentId? }` | `task-create` | Создаёт задачу, автор — текущий пользователь (`reporterId`). Правила раздела 2; `null` в `statusId`, `priority`, `parentId` равен отсутствию поля ([00, раздел 3](00-conventions.md)). Ошибки 422 с `fields` (причины: `required`, `too_long`, `invalid`, `not_member`, `not_active`, `not_found`, `reason_required`, `not_allowed`, `archived`): `title` пустое или длиннее 100; `description` длиннее 5000; `type = subtask` без `parentId` (`parentId = required`) или `parentId` у task и bug (`parentId = not_allowed`); родитель не найден в проекте (`not_found`), сам подзадача (`invalid`), архивный (`archived`); `statusId`, `subsystemId`, `tagIds` не из проекта (`not_found`); `assigneeId` и `reviewerId` не участник (`not_member`) или деактивирован (`not_active`); `dueDate` не дата; `estimateMinutes` вне 1–100000; `tagIds` больше 50 (`too_many`) или с повторами (`duplicate`). Пишет событие `created`. 201 `TaskDetail` |
| `GET /projects/:projectId/tasks/by-key/:key` | `task-view` | `TaskDetail`. `key` — `PROJ-123`, регистр не важен; проект задаётся путём (раздел 4 пакета 2), префикс ключа должен совпасть с ключом этого проекта. Нет такой задачи, префикс чужой или пользователь не участник проекта: 404 |
| `PATCH /tasks/:taskId` `{ title?, description?, type?, priority?, assigneeId?, reviewerId?, subsystemId?, dueDate?, estimateMinutes?, tagIds? }` | `task-update` | Частичное изменение: отсутствие поля — не менять, переданное меняется, `null` очищает (у `title`, `type`, `priority` `null` — 422 `fields.<поле> = invalid`). Правила и коды ошибок как при создании; дополнительно: `statusId` в теле — 422 (`fields.statusId = "use_move"`), `parentId` — 422 (`fields.parentId = "immutable"`), `type` для Subtask или значение `type = subtask` — 422 (`fields.type = "locked"`, а не `invalid`). `tagIds` — полный новый набор: бэкенд сам считает добавленные и снятые теги и пишет `tag_added`/`tag_removed` по каждому. Для не меняющихся значений событий нет. Архивная: 409 `task_archived`. 200 `TaskDetail` |
| `GET /tasks/:taskId/subtasks` | `task-view` | `{ items: [TaskSummary] }`, по возрастанию номера, без пагинации. Неархивные подзадачи; если сама задача архивная — все её подзадачи. У подзадачи ответ — пустой список. Фильтров нет |
| `POST /tasks/:taskId/archive` | `task-archive` | Архивирует задачу. Свою (`reporterId`) может любой с ключом, чужую — admin и owner (иначе 403 `forbidden`). Уже архивная: 409 `task_already_archived`. Если у задачи есть неархивные подзадачи, они архивируются вместе с ней (раздел 6). Пишет событие `archived` каждой затронутой задаче. 200 `TaskDetail` |
| `POST /tasks/:taskId/restore` | `task-restore` | Восстанавливает задачу и все её подзадачи (в том числе архивированные отдельно). Не архивная: 409 `task_not_archived`. Подзадача, чей родитель архивный: 409 `parent_archived` (сначала восстановить родителя). Пишет событие `restored` самой задаче и каждой восстановленной подзадаче. 200 `TaskDetail` |
| `GET /tasks/:taskId/history` | `task-view` | `{ items: [HistoryEvent] }`, от новых к старым, одним списком без пагинации. В событии: `id`, `kind`, `field`, `oldValue`, `newValue`, `createdAt`, `actor` (`UserRef`) |

Статус, исполнитель и ревьюер меняются на фронте так: исполнитель и ревьюер — `PATCH`, статус — `move` (пакет 6).

**Побочные эффекты (видимые клиенту).**
- `POST` задачи и `PATCH` с изменённым исполнителем или ревьюером подписывают нового исполнителя и ревьюера (а при создании и автора) на задачу ([пакет 7](07-comments-worklogs-watches.md), раздел 4); прежний исполнитель или ревьюер подписку сохраняет.
- Те же операции порождают уведомления по правилам [пакета 8](08-notifications-and-telegram.md), раздел 2; снятие исполнителя или ревьюера нового получателя не создаёт, правки прочих полей уведомлений не порождают.
- `move` никого не подписывает; описание задачи бэкенд не дополняет (шаблон описания для Bug подставляет фронт).

## 6. Архивация с подзадачами
- Архивируя Task или Bug, бэкенд ставит `archivedAt` и всем его неархивным подзадачам. Подзадачи, архивированные раньше отдельно, не затрагиваются.
- Восстановление родителя возвращает все его подзадачи, в том числе архивированные отдельно: служебного поля каскада нет, точный откат к прежнему состоянию не нужен (Q-23, I-16).
- Архивировать подзадачу отдельно можно, восстановить её отдельно — только если родитель не архивный (409 `parent_archived`).
- Всё выполняется целиком или не выполняется, в том числе при одновременных запросах ([00, раздел 9](00-conventions.md)). В ответе `TaskDetail` родителя в `subtaskCount` попадают оставшиеся неархивные подзадачи.

## 7. Подключение заготовок пакетов 2 и 3
Эти шаги заменяют пустые заготовки на реальную логику:
1. **Счётчики** `taskCount` у статусов, направлений и тегов (пакет 3) считаются по таблице задач, включая архивные.
2. **Удаление статуса** (`DELETE /statuses/:statusId?moveTo=`): все задачи статуса (включая архивные) получают `statusId = moveTo` через общую функцию «применить новый статус»: `resolvedAt` по правилу раздела 2, `rank` — в конец целевого статуса с сохранением прежнего взаимного порядка, событие `field_changed` (`field = status`) с автором — пользователем, удаляющим статус.
3. **Удаление направления** (`moveTo`): у задач поле направления меняется на `moveTo` или `null`, пишется `field_changed` (`subsystem`).
4. **Удаление тега**: связи `TaskTag` удаляются, каждой задаче пишется `tag_removed`; `updatedAt` обновляется.
5. **Удаление участника из проекта**: он снимается с исполнителя и ревьюера всех задач проекта (включая архивные), каждой пишется `unassigned_on_member_removal` (`field = assignee` или `reviewer`, `oldValue` — пользователь, `actor` — тот, кто удалил), `updatedAt` обновляется.
6. **Деактивация пользователя** задачи не меняет: исполнитель остаётся, отдаётся с `active = false`.
Все эти действия выполняются вместе с основной операцией: клиент не видит промежуточного состояния.

## 8. Тестовые данные (`DEV_SEED=true`)
К данным пакетов 1–3 добавляются задачи.
- Проект `DEMO` (около 25 задач): все статусы шаблона `dev` представлены, в том числе Cancelled и Done; 4–5 багов; 4 задачи с подзадачами (2–4 подзадачи у каждой, часть закрыта); есть задачи без исполнителя, без срока, с просроченным сроком (не закрытые), с оценкой, с тегами `release`, `tech-debt`, `ux`, с направлениями Frontend и Backend; одна архивная задача с архивированной вместе с ней подзадачей и ещё одна подзадача, архивированная отдельно (при восстановлении родителя возвращаются обе); часть задач на `fedor_inactive`; авторы (`reporterId`) — разные участники.
- Проект `SIMPLE` — 5 задач, без подзадач.
- История заполняется естественно (событие `created` у каждой задачи); добавить по 1–2 изменения полей у нескольких задач, чтобы вкладка «История» не была пустой.

## 9. Критерии приёмки
1. Создание задачи даёт ключ `KEY-N`, номера идут подряд; 20 одновременных запросов создания в одном проекте возвращают 20 разных номеров (повторить 10 раз подряд; любой дубль — провал). Создаётся событие `created`. Сид и скрипт генерации тестовых задач не создают задач с дублирующимся номером.
2. Создание Subtask: без `parentId` — 422; с родителем-подзадачей — 422 (`fields.parentId = invalid`); с архивным родителем — 422 (`fields.parentId = archived`); с родителем другого проекта — 422 (`fields.parentId = not_found`); Task/Bug с `parentId` — 422 (`fields.parentId = not_allowed`).
3. Нельзя создать задачу в статусе с `requiresReason` (422, `fields.statusId = reason_required`); без `statusId` задача попадает в первый по `position` статус без `requiresReason` (если первым после `PUT .../statuses/order` стал статус с причиной, берётся следующий; если все требуют причину — 422, `fields.statusId = required`); новая задача встаёт в конец колонки.
4. Названия длиннее 100 символов и описания длиннее 5000 дают 422 с `fields`; пробелы по краям названия отсекаются.
5. `PATCH` меняет только переданные поля, не меняющая запись ничего не пишет (нет события и `updatedAt` прежний); смена нескольких полей даёт по событию на поле с общим `createdAt`.
6. `PATCH` с `statusId` — 422 (`fields.statusId = use_move`); с `parentId` — 422 (`fields.parentId = immutable`); смена типа Task ↔ Bug работает, для Subtask — 422 (`fields.type = locked`); `PATCH` задачи Task с `type: subtask` — тоже `locked`.
7. Теги: `tagIds` заменяет набор, в истории по одному `tag_added`/`tag_removed` на каждое отличие; тег из чужого проекта — 422 (`fields.tagIds = not_found`); 51 тег — 422 (`fields.tagIds = too_many`); повтор тега — 422 (`fields.tagIds = duplicate`).
8. Исполнитель и ревьюер: не участник — 422 (`fields.assigneeId = not_member`, для ревьюера `fields.reviewerId`), деактивированный — 422 (`fields.assigneeId = not_active`, для ревьюера `fields.reviewerId`); уже назначенный и затем деактивированный отдаётся с `active = false`.
9. `GET /projects/<uuid DEMO>/tasks/by-key/proj-12` (в нижнем регистре) возвращает задачу; для не участника проекта — 404, как и для несуществующего ключа и ключа с префиксом другого проекта.
10. Архивация родителя архивирует его подзадачи и пишет `archived` каждой; восстановление родителя возвращает все его подзадачи, в том числе архивированные отдельно ранее, и пишет `restored` каждой; восстановление подзадачи при архивном родителе — 409 `parent_archived`.
11. Архивировать чужую задачу member не может (403), своё — может; admin и owner — любую; восстановить — только admin и owner.
12. Любое изменение архивной задачи, кроме восстановления, — 409 `task_archived`.
13. Счётчики `taskCount` (статусы, направления, теги) возвращают реальные числа; удаление статуса с задачами с `moveTo` переносит все задачи (включая архивные), ставит `resolvedAt` по категории и пишет событие; без `moveTo` — 409 `move_to_required`; удаление направления, тега и участника ведёт себя по разделу 7.
14. `GET /tasks/:id/subtasks`: порядок по номеру; архивные подзадачи не показываются, если родитель не архивный; суммы `subtasksEstimateMinutes` и `subtasksDone` в `TaskDetail` родителя соответствуют неархивным подзадачам.
15. `isOverdue` верно для задач с прошедшим сроком в статусе не `done` и ложно для закрытых и архивных.
16. История: `GET /tasks/:id/history` отдаёт события от новых к старым; `label` в значениях остаётся прежним после переименования справочника.
17. В OpenAPI у каждой ручки есть `x-permission`; схемы `TaskSummary`, `TaskDetail`, `HistoryEvent` описаны один раз (проверка — правило линтера: схемы подключаются через `$ref`, дублей нет).
18. Одновременные запросы (по [00, раздел 9](00-conventions.md)): `POST` подзадачи одновременно с `POST /tasks/:id/archive` родителя — подзадача либо создана и заархивирована вместе с ним, либо создание отвечает 422 (`fields.parentId = archived`); активной подзадачи под архивным родителем не остаётся (повторить не менее 20 раз).
19. После `POST /admin/users/:id/reissue` для участника проекта `PATCH /tasks/:taskId` с его `assigneeId` проходит (200), участник отдаётся с `active = true`; для деактивированного — 422 (`fields.assigneeId = not_active`).
20. История значений: событие `created`, `archived`, `restored` — `field`, `oldValue`, `newValue` равны `null`; `tag_added` — `newValue = { id, label }`; `tag_removed` — `oldValue = { id, label }`; `unassigned_on_member_removal` — `field = assignee` или `reviewer`, `oldValue` — снятый пользователь.
21. Подписки: после `POST` задачи с исполнителем и ревьюером `TaskDetail.watching` у автора, исполнителя и ревьюера равно `true`; после смены исполнителя `PATCH` новый подписан, прежний остался подписанным.

## 10. Открытые вопросы
1. **Решено:** новая задача — в конец колонки (раздел 2; страница доски — [07-boards-page.md](../07-boards-page.md), «Порядок»).
2. **Решено:** максимальная оценка 100000 минут, срок — любая дата, в том числе прошлая (раздел 2); ограничения списаний времени — [пакет 7](07-comments-worklogs-watches.md), раздел 3.
3. **`isOverdue` по дате UTC.** Для человека в другом часовом поясе красная метка может переключиться на несколько часов раньше или позже полуночи; для учебного проекта это допустимо. Фронт вправе пересчитать признак по `dueDate` и локальной дате ([00, раздел 12](00-conventions.md)).
4. **Решено:** `updatedAt` обновляется и от комментариев (добавление, правка, удаление), но не от списаний времени. Реализуется в пакете 7 через общую функцию «отметить задачу изменённой».

## 11. Рекомендации (необязательно)
- **Нумерация.** Номер брать из счётчика проекта одним атомарным обновлением (`UPDATE … SET taskSeq = taskSeq + 1 RETURNING`) и подстраховать уникальным ограничением `UNIQUE(projectId, number)`; сид и скрипты генерации используют тот же счётчик.
- **Родитель.** При создании подзадачи брать `FOR SHARE` строки родителя, при архивации родителя — `FOR UPDATE` ([00, раздел 13](00-conventions.md)); всю архивацию с подзадачами делать одной транзакцией.
- **Порядок карточек.** Колонку `rank` хранить с побайтовой сортировкой (`COLLATE "C"` или `bytea`), индекс `(statusId, rank)` строить в той же сортировке; алгоритм — [06](06-boards-and-move.md), раздел 10.
- **Общие операции.** `applyStatus` (поля `statusId`, `rank`, `resolvedAt`, `updatedAt`, событие истории), `recordHistory` (одна `createdAt` на запрос), `touchTask`, публикация доменных событий после коммита — вынести один раз и вызывать из пакетов 3, 5, 6, 7.
- **Подключение заготовок.** Шаги раздела 7 (перенос задач, снятие тегов и участников) выполнять в той же транзакции, что и основная операция.
- **Индексы и ключи.** См. [13](../13-data-model-and-permissions.md), раздел 7.
