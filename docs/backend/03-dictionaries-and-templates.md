## 1. Цель и границы
Дать фронту справочники проекта (статусы, доски, направления, теги) и наполнение проекта по шаблону при создании.
- Входит: Status, Board, BoardColumn, Subsystem, Tag; ручки раздела 5; шаблоны `dev` и `simple` (раздел 4); тестовые данные.
- Не входит: задачи и привязка тегов к задачам (пакет 4), карточки на досках и перенос (пакет 6). Поэтому в пакете 3 счётчики `taskCount` везде равны 0, перенос задач при удалении статуса и направления и снятие тегов с задач заготовлены как шаги, которые пакет 4 наполняет логикой (раздел 7).
- Фронт реализует разделы «Статусы» и «Доски» настроек позже ядра, но API делается сразу целиком: ядру нужны чтение статусов и досок, шаблон и ручки направлений и тегов.

## 2. Общие правила
- Все справочники принадлежат проекту; связь с другим проектом невозможна (проверяется во всех ручках: идентификатор из чужого проекта в пути — 404, в теле или query — 422 `fields`, см. [00, раздел 3](00-conventions.md)).
- **Названия** (статуса, доски, направления, тега): строка после `trim`, 1–100 символов; уникальны внутри своего списка в проекте без учёта регистра. Повтор: 409 `name_taken` с `fields.name = "taken"`. Пустое после `trim`: 422 `validation_failed`, `fields.name = "required"`. Проверка уникальности не считает саму запись: переименование «Frontend» в «frontend» — 200.
- Права: изменение — ключ раздела (`status-manage`, `board-manage`, `subsystem-manage`, `tag-manage`; создание тега на лету — `tag-create`). Чтение: статусы — `project-view`, доски — `board-view`, направления и теги — `task-view`.
- Интерфейса управления статусами и досками в первой версии нет (после релиза, Q-05): статусы и доски создаёт шаблон, ручки изменения остаются в контракте и принимаются по критериям ниже.
- Списки отдаются целиком, без пагинации. Пределов на число статусов, досок, направлений и тегов нет.
- Идентификаторы в путях — UUID. Ресурсы адресуются как `/statuses/:statusId` и т. п.; проект определяется по ресурсу, если его нет или он чужой — 404.

## 3. Сущности

**Status:** `id`, `name`, `color`, `category`, `requiresReason`, `position`.
- `color` — одно из 8 фиксированных значений: `gray`, `blue`, `cyan`, `green`, `yellow`, `orange`, `red`, `purple` (фронт сопоставляет цвета токенам Taiga UI; произвольных цветов нет).
- `category`: `backlog`, `todo`, `in_progress`, `done`. Категория `done` означает «закрыто»: `resolvedAt` у задач, окно Done на досках, срок не краснеет. Остальные категории пока только описательные.
- `position` — целое от 0; порядок статусов в списке выбора и в таблице настроек; новый статус добавляется в конец.
- В проекте всегда есть минимум один статус категории `done`.
- Смена категории существующего статуса `resolvedAt` у уже имеющихся задач не пересчитывает.

**Board:** `id`, `name`, `columns`, `baseFilter`, `doneWindowDays`, `createdAt`.
- `columns` — упорядоченный список статусов проекта (`statusId`), минимум 1, без повторов. В ответах колонка содержит и справочные поля статуса: `{ statusId, name, color, category, requiresReason }` (по `requiresReason` доска сразу знает, что при переносе в колонку нужен диалог причины).
- `doneWindowDays`: целое 1–365, по умолчанию 14. Хранится всегда, учитывается только если среди колонок есть статус категории `done`.
- `baseFilter` — объект, все поля необязательны, каждое — массив значений. Ограничивает карточки доски:
  - `assigneeIds`, `reviewerIds`: UUID участников проекта или строка `none` (не назначен);
  - `priorities`: `low`, `medium`, `high`, `critical`;
  - `types`: `task`, `bug`, `subtask`;
  - `subsystemIds`: UUID направлений проекта или `none` (без направления);
  - `tagIds`: UUID тегов проекта.
  Смысл: значения внутри одного поля объединяются по «или», разные поля — по «и»; отсутствующее или пустое поле ничего не ограничивает. Статуса в фильтре нет. Значение `me` («Я») в базовом фильтре не допускается (оно относится к пользовательским фильтрам). Неизвестные поля — 422.
- Доски отдаются в порядке создания (шаблон `dev` создаёт «Разработку», затем «Планирование»; поля порядка в контракте нет). В проекте всегда минимум одна доска.

**Subsystem («Направление»):** `id`, `name`. Других свойств нет.

**Tag:** `id`, `name`. Теги создаются на лету из задачи (право `tag-create`), переименовываются и удаляются в настройках (право `tag-manage`).

## 4. Шаблоны проекта
Шаблон применяется один раз при создании проекта: проект либо создан целиком вместе со статусами, досками и направлениями шаблона, либо не создан. Дальше проект живёт сам по себе: изменение шаблона на существующие проекты не влияет.

### `dev` («Dev team»)
Статусы (по порядку):
| Позиция | Название | Категория | Цвет | Причина (`requiresReason`) |
|---|---|---|---|---|
| 0 | Backlog | `backlog` | `gray` | нет |
| 1 | PBR | `backlog` | `purple` | нет |
| 2 | Plan | `todo` | `blue` | нет |
| 3 | To do | `todo` | `cyan` | нет |
| 4 | Reopened | `todo` | `orange` | нет |
| 5 | In progress | `in_progress` | `yellow` | нет |
| 6 | In review | `in_progress` | `purple` | нет |
| 7 | In test | `in_progress` | `blue` | нет |
| 8 | For release | `in_progress` | `cyan` | нет |
| 9 | Blocked | `in_progress` | `red` | **да** |
| 10 | Done | `done` | `green` | нет |
| 11 | Cancelled | `done` | `gray` | **да** |

Доски (в таком порядке создания; первая — та, что открывается по умолчанию):
1. **Разработка**: To do, Reopened, In progress, In review, In test, For release, Blocked, Done. Базовый фильтр пустой, окно Done 14 дней.
2. **Планирование**: Backlog, PBR, Plan, To do. Базовый фильтр пустой, окно Done 14 дней.

Колонки Cancelled нет ни на одной доске: статус ставится в карточке. Статус To do есть на обеих досках.
Направления: Frontend, Backend. Тегов нет.

### `simple`
Статусы: To do (`todo`, `cyan`), In progress (`in_progress`, `yellow`), Done (`done`, `green`), Cancelled (`done`, `gray`, причина обязательна).
Доска: **Основная** с колонками To do, In progress, Done; фильтр пустой, окно Done 14 дней. Направлений нет (поле скрыто на фронте, пока справочник пуст), тегов нет.

Названия досок и направлений — по-русски/латиницей ровно как в таблицах; названия статусов — на английском, как в документах.

## 5. Ручки
Права: ключи из документа 13. Ошибки — по общему формату; общие коды 401/403/404 описаны в пакете 2.

### Статусы
Элемент: `Status = { id, name, color, category, requiresReason, position, taskCount, boards: [{ id, name }] }`; `taskCount` — число всех задач проекта в этом статусе, включая архивные; `boards` — доски, где статус является колонкой.
| Ручка | Права | Поведение |
|---|---|---|
| `GET /projects/:projectId/statuses` | `project-view` | `{ items: [Status] }` по возрастанию `position` |
| `POST /projects/:projectId/statuses` `{ name, color, category, requiresReason? }` | `status-manage` | Создаёт статус в конец списка; `requiresReason` по умолчанию `false`. 201 `Status`. Ошибки: 422 (`fields`: `name`, `color`, `category`), 409 `name_taken` |
| `PATCH /statuses/:statusId` `{ name?, color?, category?, requiresReason? }` | `status-manage` | Частичное изменение. Если статус единственный категории `done` и категория меняется: 409 `last_done_status` (в том числе при одновременных запросах, [00, раздел 9](00-conventions.md)). Остальные ошибки как при создании. 200 `Status` |
| `PUT /projects/:projectId/statuses/order` `{ ids: [uuid] }` | `status-manage` | Задаёт порядок: `ids` должен содержать все статусы проекта ровно по одному разу, иначе 422 (`fields.ids = "mismatch"`). Позиции пересчитываются от 0. 200 `{ items: [Status] }` |
| `DELETE /statuses/:statusId?moveTo=<statusId>` | `status-manage` | Правила ниже. 204 |

**Удаление статуса.**
1. Единственный статус категории `done`: 409 `last_done_status` (в том числе при одновременных запросах, [00, раздел 9](00-conventions.md)).
2. Если в статусе есть задачи (включая архивные), `moveTo` обязателен: нет — 409 `move_to_required`. `moveTo` должен быть другим статусом того же проекта, иначе 422 (`fields.moveTo = "invalid"`). Если задач нет, `moveTo` игнорируется. Перенос при удалении — системный: он не требует причины, даже если у `moveTo` стоит `requiresReason` (запрет создавать задачу в такой статус его не касается), и комментарий `status_reason` не создаётся.
3. Если статус — единственная колонка какой-либо доски, удаление запрещено: 409 `board_would_be_empty`, `details.boards = [названия]` (доску сначала нужно изменить или удалить). Во всех остальных досках колонка с этим статусом убирается.
4. Операция выполняется целиком или не выполняется: перенос задач (раздел 7), удаление колонок, пересчёт `position` оставшихся статусов подряд, удаление статуса.

### Доски
Элемент: `Board = { id, name, columns: [{ statusId, name, color, category, requiresReason }], baseFilter, doneWindowDays, createdAt }`.
| Ручка | Права | Поведение |
|---|---|---|
| `GET /projects/:projectId/boards` | `board-view` | `{ items: [Board] }` в порядке создания |
| `GET /boards/:boardId` | `board-view` | `Board`; чужой или несуществующий: 404 |
| `POST /projects/:projectId/boards` `{ name, columns: [statusId], baseFilter?, doneWindowDays? }` | `board-manage` | Создаёт доску. `columns` — упорядоченный список статусов проекта, минимум 1, без повторов (иначе 422, `fields.columns = "empty"`, `"duplicate"` или `"invalid"`). `baseFilter` проверяется по разделу 3 (ссылки на несуществующие или чужие сущности: 422, `fields.baseFilter`). `doneWindowDays` вне 1–365: 422. 201 `Board` |
| `PATCH /boards/:boardId` `{ name?, columns?, baseFilter?, doneWindowDays? }` | `board-manage` | Частичное изменение; `columns` и `baseFilter`, если переданы, заменяются целиком. Правила как при создании. Изменение применяется к доске сразу. 200 `Board` |
| `DELETE /boards/:boardId` | `board-manage` | Задачи не затрагиваются. Последняя доска проекта: 409 `last_board` (в том числе при одновременных запросах, [00, раздел 9](00-conventions.md)). 204 |

### Направления
Элемент: `Subsystem = { id, name, taskCount }`.
| Ручка | Права | Поведение |
|---|---|---|
| `GET /projects/:projectId/subsystems` | `task-view` | `{ items: [Subsystem] }`, порядок по названию (без учёта регистра) |
| `POST /projects/:projectId/subsystems` `{ name }` | `subsystem-manage` | 201 `Subsystem`; 409 `name_taken` |
| `PATCH /subsystems/:subsystemId` `{ name }` | `subsystem-manage` | 200 `Subsystem`; 409 `name_taken` |
| `DELETE /subsystems/:subsystemId?moveTo=<subsystemId \| none>` | `subsystem-manage` | Если у направления есть задачи (включая архивные), `moveTo` обязателен (иначе 409 `move_to_required`): другое направление проекта либо `none` («без направления», у задач `subsystemId = null`). Неверное значение: 422 (`fields.moveTo = "invalid"`). Если задач нет, `moveTo` игнорируется. Из `baseFilter` досок удаляется это значение. 204 |

### Теги
Элемент: `Tag = { id, name, taskCount }`.
| Ручка | Права | Поведение |
|---|---|---|
| `GET /projects/:projectId/tags?search=` | `task-view` | `{ items: [Tag] }`, порядок по названию; `search` — вхождение без учёта регистра |
| `POST /projects/:projectId/tags` `{ name }` | `tag-create` | Создание на лету из задачи. 201 `Tag`; такое имя уже есть: 409 `name_taken` с `fields.name = "taken"` и `details.tag` — существующим тегом (фронт перед созданием показывает существующие теги; при гонке подставляет `details.tag`) |
| `PATCH /tags/:tagId` `{ name }` | `tag-manage` | Переименование, 200 `Tag`; 409 `name_taken` |
| `DELETE /tags/:tagId` | `tag-manage` | Тег снимается со всех задач проекта (раздел 7), сами задачи остаются; значение удаляется из `baseFilter` досок. 204 |

## 6. Сквозные правила
- **Чистка базового фильтра.** При удалении направления или тега их идентификаторы убираются из `baseFilter` всех досок проекта. Если поле фильтра стало пустым, оно перестаёт ограничивать выборку. То же при удалении участника из проекта (идентификатор убирается из `assigneeIds` и `reviewerIds`): правило добавляется к ручке удаления участника пакета 2.
- **Журнал событий безопасности:** изменения справочников не пишутся (это обычные правки данных), история задач пишется при переносе и снятии (раздел 7).
- Удаление и переименование применяются сразу везде: фронт всегда читает справочники с сервера, статусы в ответах задач и карточек возвращаются с актуальными именем и цветом.

## 7. Что подключает пакет 4
В пакете 3 задач нет, поэтому шаги ниже реализуются как вызовы пустых заготовок, а пакет 4 наполняет их:
1. **Перенос задач при удалении статуса.** Все задачи статуса получают `statusId = moveTo`, оказываются в конце целевой колонки с сохранением прежнего взаимного порядка (новые `rank` считает бэкенд). `resolvedAt` ведётся по общему правилу: ставится, если целевой статус категории `done` и значения не было; сбрасывается, если целевой статус не `done`. В историю каждой задачи пишется смена статуса (автор — пользователь, удаляющий статус).
2. **Перенос задач при удалении направления.** Поле направления меняется на `moveTo` или `null`, в историю пишется смена направления.
3. **Снятие тега.** Связи `TaskTag` удаляются, в историю каждой задачи пишется `tag_removed`.
4. **Счётчики** `taskCount` у статусов, направлений и тегов считаются запросами по задачам (все, включая архивные).

## 8. Тестовые данные (`DEV_SEED=true`)
К данным пакетов 1–2 добавляется: статусы, доски и направления проектов создаются шаблонами (`DEMO` — `dev`; `SIMPLE` — `simple`); в `DEMO` дополнительно теги `release`, `tech-debt`, `ux`; в `DEMO` дополнительная доска «Frontend» с базовым фильтром `subsystemIds = [Frontend]` (пример доски-фильтра).

## 9. Критерии приёмки
1. Создание проекта шаблоном `dev` даёт 12 статусов, 2 доски в порядке «Разработка», «Планирование» и 2 направления ровно по разделу 4; шаблон `simple` — 4 статуса и 1 доску. Проект создаётся вместе с содержимым шаблона: при ошибке проекта нет вовсе.
2. Чтение статусов, досок, направлений и тегов разрешено viewer, изменение — только по ключам (member получает 403 на изменение статусов, досок и направлений, но может создать тег).
3. Повторное название (в том числе в другом регистре и с пробелами по краям) даёт 409 `name_taken` для статуса, доски, направления и тега; одно и то же название в разных проектах допустимо; переименование записи в то же имя в другом регистре («Frontend» → «frontend») — 200.
4. Статус нельзя перевести в другую категорию или удалить, если он единственный категории `done` (409 `last_done_status`).
5. Удаление статуса: без задач — проходит; с задачами без `moveTo` — 409 `move_to_required` (проверяется после подключения пакета 4); статус, единственный в колонках доски, даёт 409 `board_would_be_empty` со списком досок; из остальных досок колонка убирается; позиции оставшихся статусов подряд от 0.
6. `PUT .../statuses/order` с неполным или избыточным списком даёт 422; корректный меняет порядок в следующем `GET`.
7. Доска: нельзя создать без колонок, с повторяющимися колонками, со статусом чужого проекта; `doneWindowDays` вне 1–365 — 422; в `baseFilter` недопустимы статус, значение `me` и неизвестные поля.
8. Последнюю доску проекта удалить нельзя (409 `last_board`); удаление остальных проходит.
9. Удаление направления и тега чистит `baseFilter` досок (проверить на доске «Frontend» из тестовых данных).
10. Идентификатор справочника из другого проекта в ручках `/statuses/:statusId` и аналогичных даёт 404 для пользователя, не состоящего в том проекте, и 403 для участника без права.
12. В OpenAPI у каждой ручки есть `x-permission`; перечисления `StatusColor`, `StatusCategory`, `Priority`, `TaskType` описаны там один раз и используются в схемах через `$ref` (дублей нет).
13. `GET /boards/:boardId` отдаёт колонки в порядке доски со справочными полями статуса, `baseFilter` и `doneWindowDays`; чужая или несуществующая доска — 404.
14. `PATCH /boards/:boardId`: `columns` и `baseFilter` заменяются целиком; те же 422 (`fields.columns`, `fields.baseFilter`, `doneWindowDays`) и 409 `name_taken`, что при создании; `PATCH` без полей не меняет доску.
15. Одновременные запросы (по [00, раздел 9](00-conventions.md)): два одновременных `DELETE` последних двух досок оставляют одну доску (второй — 409 `last_board`); два одновременных `PATCH` категории двух статусов `done` либо `DELETE` двух статусов `done` оставляют минимум один статус `done`; два одновременных `POST` тега с одним именем дают 201 и 409 `name_taken` с `details.tag`; два одновременных `POST` статуса, доски или направления с одним именем дают 201 и 409 `name_taken`.
16. Удаление статуса с задачами при `moveTo` на статус с `requiresReason`: 204, задачи перенесены без причины, комментарий `status_reason` не создан, в истории каждой задачи есть смена статуса; создание задачи в тот же статус по-прежнему даёт 422 (`fields.statusId = reason_required`).
17. `GET /projects/<uuid>/boards` для проекта шаблона `dev` отдаёт первой доску «Разработка», второй «Планирование»; колонки досок содержат `requiresReason` (у Blocked — `true`).

## 10. Открытые вопросы
Открытых вопросов нет. Решено ментором: категории статусов шаблона `dev`, палитра цветов и названия по умолчанию (доски «Разработка», «Планирование», «Основная»; направления Frontend, Backend) приняты; статус Cancelled есть в обоих шаблонах (`dev` и `simple`) и не имеет колонки ни на одной доске (ставится в карточке); запрет удаления статуса, единственного на доске, принят.

## 11. Рекомендации (необязательно)
- **Уникальность.** Имя уникально в проекте без учёта регистра — уникальный индекс по `(projectId, lower(name))`; повтор при гонке перехватывать по имени ограничения и отвечать 409 `name_taken`.
- **Последний `done` и последняя доска.** Проверку и запись выполнять в одной транзакции под блокировкой строки проекта (`SELECT … FOR UPDATE`), порядок блокировок — [00, раздел 13](00-conventions.md).
- **Порядок досок.** Хранить порядок создания явно (время создания с достаточной точностью плюс идентификатор) и создавать доски шаблона последовательно: «Разработка» первой.
- **Шаблоны.** Содержимое шаблонов `dev` и `simple` держать в коде константой, применять в той же транзакции, что и создание проекта.
- **Внешние ключи.** `Task` → `Status` RESTRICT (статус удаляется через `moveTo`), `BoardColumn` → `Board` CASCADE, `TaskTag` → `Tag` CASCADE после записи `tag_removed`; индексы — [13](../13-data-model-and-permissions.md), раздел 7.
