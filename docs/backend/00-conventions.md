# ТЗ бэкенда: общие соглашения

Относится ко всем пакетам ТЗ. Продукт и поведение описаны в документах `docs/01, 02, 04–13`; модель данных и ключи разрешений — в [13-data-model-and-permissions.md](../13-data-model-and-permissions.md). Контракт API — [openapi/openapi.yaml](openapi/openapi.yaml) (растёт пакетами). Кто главнее при расхождении, зависит от темы: пути, поля, коды ошибок и лимиты — OpenAPI; роли и ключи прав — документ 13, раздел 4; поведение бэкенда — эти пакеты ТЗ (см. [README](../README.md), «Иерархия источников»). Расхождение надо сообщить.

**Что обязательно.** В каждом пакете ТЗ обязательны только две вещи: **контракт** (OpenAPI: пути, поля, обязательность, форматы, лимиты, статусы, коды ошибок, права) и **наблюдаемое поведение** (что клиент получает в ответ и что после запроса видят пользователи, включая видимые инварианты). Разделы пакета до раздела «Рекомендации (необязательно)» — требования, критерии приёмки проверяются через API без доступа к коду. Последний раздел каждого пакета — «Рекомендации (необязательно)»: СУБД, индексы, блокировки, транзакции, алгоритмы, порядок внутренних проверок, очереди, логи и тесты решает разработчик бэкенда, рекомендации можно не выполнять.

## 2. Протокол
- Технологии и СУБД выбирает разработчик бэкенда. Обязателен только контракт.
- Базовый путь `/api`, формат JSON (`Content-Type: application/json`), кодировка UTF-8.
- Идентификаторы сущностей — строки (UUID); у задач есть читаемый ключ `PROJ-123` (поиск и адреса работают по ключу).
- Даты и время — ISO 8601 в UTC (`2026-11-03T10:15:00Z`); дата без времени (срок, дата списания) — `2026-11-03`. Длительности — целое число минут. Дату без времени фронт хранит и передаёт строкой (или `TuiDay`), а не `Date`: иначе западнее UTC она сдвигается на сутки. «Сегодня» на бэкенде — дата по UTC, поэтому фронт всегда передаёт `date` явно (раздел 12).
- Имена полей и ключи объектов в JSON — `camelCase`; значения перечислений, коды ошибок и причины в `fields` — строки `snake_case` (`in_progress`, `last_owner`, `not_member`).
- В ответах пустые необязательные значения — `null`, а не отсутствие поля. Необязательная строка, пришедшая пустой (или из одних пробелов), сохраняется и отдаётся как `null`.
- **`null` в запросах — одно правило:** в `POST` `null` равен отсутствию поля; в `PATCH` отсутствие поля — не менять, `null` — очистить (где поле очищаемо; у неочищаемых полей — 422 `invalid`). Поля запроса, у которых `null` допустим, помечены `nullable: true` в OpenAPI.
- Строки в теле (названия, имена, тексты) перед проверкой длины обрезаются по краям (`trim`); пустое после обрезки обязательное поле — 422 (`fields.<поле> = required`).

## 3. Ошибки
Единый формат тела при статусе 4xx и 5xx:
```json
{ "error": { "code": "validation_failed", "message": "Проверьте поля формы", "fields": { "title": "too_long" } } }
```
- `code` — стабильная строка в snake_case (`last_owner`, `project_key_taken`) для фронта из перечня `ErrorCode`;
- `message` — текст на русском для показа пользователю;
- `fields` — только для ошибок валидации (422) и 409 `name_taken`: ключ — имя поля запроса, значение — причина из перечня `FieldErrorReason`;
- `details` — необязательные данные для показа, состав по кодам в таблице ниже;
- `requestId` — только в теле 5xx (раздел 6).

**Нарушение схемы → причина в `fields`.** Если запрос не проходит ограничение схемы OpenAPI, причина всегда такая:

| Нарушение схемы | `fields.<поле>` |
|---|---|
| обязательное поле отсутствует (или пусто после `trim`) | `required` |
| `maxLength` | `too_long` |
| `maxItems` | `too_many` |
| `uniqueItems` | `duplicate` |
| `enum` или `format` (в том числе неверный тип и `null` у неочищаемого поля) | `invalid` |

Нарушения, которые схема не выражает (`type = subtask` в `PATCH` → `locked`, и подобные), описаны прямо в операции и в OpenAPI. Если у операции причина указана отдельно, действует она.

Перечни `ErrorCode` и `FieldErrorReason` заданы в OpenAPI (`components.schemas`) и совпадают с таблицами ниже. Новый код сначала добавляется в OpenAPI. Причина валидации — это не `code`: 422 всегда `validation_failed`, а причина лежит в `fields`. В ТЗ пакетов она пишется так: «422 (`fields.<поле> = <причина>`)». Ответы 400 (`bad_request`) и 500 (`internal_error`) объявлены у каждой операции через общие ответы `BadRequest` и `InternalError`.

| HTTP | Когда | Типовые `code` |
|---|---|---|
| 400 | неверный формат запроса | `bad_request` |
| 401 | нет сессии | `unauthenticated`, `invalid_credentials` |
| 403 | нет права | `forbidden`, `account_deactivated`, `password_change_required` |
| 404 | не найдено или скрыто | `not_found`, `invitation_invalid` |
| 409 | конфликт состояния | `username_taken`, `telegram_already_linked`, `last_login_method`, `telegram_not_linked`, `last_owner`, `user_deactivated`, `cannot_reissue_self`, `cannot_deactivate_self`, `project_key_taken`, `already_member`, `already_owner`, `owner_role_locked`, `cannot_change_self`, `cannot_remove_self`, `name_taken` (повтор названия справочника, с `fields.name = "taken"`), `move_to_required`, `last_done_status`, `last_board`, `board_would_be_empty`, `task_archived`, `parent_archived`, `task_already_archived`, `task_not_archived`, `link_exists`, `link_cycle`, `stale_position` |
| 422 | не прошла валидация | `validation_failed` |
| 429 | превышен лимит | `too_many_attempts` (заголовок `Retry-After`) |
| 5xx | ошибка сервера | `internal_error` |
Сообщения об ошибках не раскрывают лишнего: при входе всегда `invalid_credentials`, не уточняя, неверен логин или пароль. Каждый объявленный в OpenAPI 409 перечисляет свои `code`; код, которого нет в описании операции, бэкенд не возвращает.

**Причины в `fields`** (`FieldErrorReason`): `required`, `invalid`, `too_long`, `too_many`, `taken`, `immutable`, `locked`, `mismatch`, `empty`, `duplicate`, `limit`, `not_found`, `not_active`, `not_member`, `not_allowed`, `reason_required`, `archived`, `same_task`, `use_move`, `in_future`, `invalid_order`.

**`details` по кодам:**
| `code` | `details` |
|---|---|
| `last_owner` | `projects` — названия проектов, где человек единственный owner |
| `board_would_be_empty` | `boards` — названия досок, где статус единственная колонка |
| `already_member` | `userIds` — UUID пользователей, которые уже участники |
| `name_taken` (тег) | `tag` — существующий тег `{ id, name, taskCount }` (гонка при создании тега на лету) |
У остальных кодов `details` нет.

**Какой id — какая ошибка.** Идентификатор в пути (или не UUID в пути) — 404 `not_found`. Идентификатор в теле или query, которого нет в проекте, — 422 (`fields.<поле> = not_found`); если пользователь существует, но деактивирован, — `not_active`, если он не участник проекта — `not_member`. Исключения: значения фильтров списков (раздел 12) — корректный UUID, которого нет в проекте, там игнорируется; соседи `prevId` и `nextId` в `move` — сосед, не найденный в проекте, архивированный или находящийся в другом статусе, даёт 409 `stale_position` ([06](06-boards-and-move.md)).

**Пароль.** Слабый пароль (короче 8 символов, нет буквы или цифры) — 422 (`fields.<поле> = invalid`), длиннее 128 — `too_long`.

## 4. Аутентификация и права
- Сессия в httpOnly cookie `sid` (подробности — в пакете 1); все ручки, кроме явно публичных, требуют сессии, иначе 401.
- Права проверяются по ключам из документа 13. В OpenAPI у каждой ручки: `x-permission: <ключ>` либо `x-permission: none` (требуется только вход) либо `x-public: true`.
- Ответ 403 не раскрывает существование ресурса, к которому нет доступа: если пользователь не участник проекта, то 404.
- Порядок ответов в ручках проекта, видимый клиенту (нет сессии → 401, не участник или нет ресурса → 404, нет права → 403, затем правила ручки), параметр `:projectId` (только UUID) и список ключей по ролям — в [02-projects-members-permissions.md](02-projects-members-permissions.md), разделы 3–5. Это поведение одинаково для пакетов 2–6.
- Права проекта не кешируются на стороне клиента между запросами: изменение роли или удаление из проекта действует на следующем же запросе.

## 5. Списки и пагинация
Пагинация только там, где она описана в ТЗ пакета: `page` и `size` (страница с 1, размер из `10 | 25 | 50`) с ответом `{ items, total }`, либо курсор `before` и `limit` с ответом `{ items, hasMore }`. Остальные списки отдаются целиком. Сортировка — параметр `sort=поле:asc|desc` из разрешённого перечня значений конкретной ручки (значение вне перечня — 422, `fields.sort = invalid`). Текстовые параметры `q` и `search` — не длиннее 100 символов, иначе 422 (`fields.q = too_long`); после `trim` пустое значение означает «фильтра нет». Списки значений в query (`status`, `assignee` и т. п.) передаются через запятую (`style: form`, `explode: false`); повтор одного значения — не ошибка (дубли отбрасываются, закладки не ломаются), больше 50 значений — 422 (`fields.<параметр> = too_many`). Фильтры по неизвестным идентификаторам и устройство курсора — раздел 12.

## 6. Безопасность
- Cookie `sid`: `HttpOnly`, `SameSite=Lax`, `Secure` в продакшене, `Path=/`.
- Для запросов, меняющих данные (не GET), проверяется заголовок `Origin` (или `Referer`) на соответствие разрешённому origin приложения. Нет ни `Origin`, ни `Referer`: 403 `forbidden`. Единственное исключение — `POST /telegram/webhook` (его защищает секрет, пакет 8).
- Для не-GET запросов с телом обязателен `Content-Type: application/json`, иначе 400 `bad_request`.
- Во всех ответах `Referrer-Policy: no-referrer`: токены приглашений лежат в адресе страницы и не должны уходить в `Referer`.
- Фронт и `/api` должны открываться с одного origin: иначе cookie `sid` (`SameSite=Lax`) не будет отправляться. Остальное (хостинг, адреса стендов) решает разработчик бэкенда. CORS разрешён только для origin из конфигурации, `credentials: true`. `ALLOWED_ORIGINS` в разработке включает `http://localhost:4200`: проверка `Origin` (см. выше) смотрит на него, а прокси dev-сервера меняет только `Host`, не `Origin`.
- Пароли, хеши паролей, идентификаторы и токены сессий никогда не возвращаются в ответах. Токены приглашений и Telegram-запросов выдаются клиенту один раз при создании (ссылка-приглашение, `token` и `deepLink`) и неугадываемы.
- Каждый ответ содержит заголовок `X-Request-Id` (значение из запроса, если он его передал, иначе новое); в теле ответа 5xx то же значение лежит в `error.requestId`; текст исключения и стек в ответ не попадают.
- Старт с `DEV_SEED=true` в продакшене запрещён: приложение завершается с ошибкой. У `DEV_SEED_PASSWORD` нет значения по умолчанию: без явно заданного пароля `DEV_SEED=true` не стартует.

## 7. Конфигурация (переменные окружения)
Обязательны для поведения, видимого снаружи: `APP_BASE_URL` (для ссылок-приглашений), `ALLOWED_ORIGINS`, `SESSION_TTL_DAYS`, `INVITATION_TTL_DAYS` (по умолчанию 7), `TELEGRAM_BOT_TOKEN`, `TELEGRAM_BOT_USERNAME`, `TELEGRAM_MODE` (`webhook` | `polling`), `TELEGRAM_WEBHOOK_SECRET`, `INITIAL_ADMIN_USERNAME`, `INITIAL_ADMIN_PASSWORD`, `DEV_SEED` (включает тестовые данные, только вне продакшена, см. раздел 6), `DEV_SEED_PASSWORD` (без значения по умолчанию). Остальные переменные (подключение к хранилищу, уровень логов, признак продакшена и т. п.) задаёт разработчик бэкенда.

## 8. Документация API и данные для разработки
- Ответы бэкенда соответствуют схемам `openapi.yaml`: пути, поля, обязательность, форматы, статусы и коды ошибок.
- У каждой операции есть `operationId` в `camelCase`: глагол и сущность (`createTask`, `listBoards`, `moveTask`), уникален во всём файле. Из него клиент получает имена методов, поэтому ручка без `operationId` не принимается. Строка `x-permission` (или `x-public`) дублируется в `description` операции. Ответы 400, 401, 403, 404, 409, 422 и 500 подключаются через `components/responses`.
- **Источник истины контракта** — `docs/backend/openapi/openapi.yaml` в репозитории фронта; бэкенд должен с ним совпадать.
- **Версионирование.** `info.version` — semver. Любое изменение контракта (ручка, схема, поле, enum, пример) оформляется PR с повышением minor (`0.2.0` → `0.3.0`) и строкой в [openapi/CHANGELOG.md](openapi/CHANGELOG.md): дата, версия, что изменилось, откуда решение (находка или вопрос). Ломающие изменения (удалить или переименовать ручку, поле или значение enum, сменить тип или обязательность) допускаются только с согласия ментора и помечаются в CHANGELOG словом «Ломающее». Бэкенд не меняет контракт «по месту»: сначала правка файла, затем реализация.
- **Конвейер на фронте.** Предложение фронту, не требование к бэкенду: генерировать типы `openapi-typescript` (только типы, без сервисов) в `src/app/api/generated/`, скриптом `npm run api:gen` (скрипта и папки в репозитории пока нет — их создаёт фронт или ментор в каркасе). Сервисы — тонкие обёртки на `HttpClient`, чтобы работали интерцепторы 401/403; имена методов повторяют `operationId`.
- **Проверка в CI.** `api:gen` и шаг CI предлагаются фронту; это не требование к бэкенду. Предлагаемый шаг (в `.github/workflows/ci.yml` его пока нет): `npx @redocly/cli lint` (0 ошибок; допустимые предупреждения — только `info-license` и `tag-description`) → `npm run api:gen` → `git diff --exit-code src/app/api/generated`; ключи `x-permission` и [таблица 13 §5](../13-data-model-and-permissions.md) сверяются с enum вручную. Для бэкенда обязательно одно: ответы соответствуют `openapi.yaml`.
- **Тип `Permission`** на фронте — объединение `GlobalPermission | ProjectPermission` из enum схем; `x-permission` генераторы не читают, их соответствие enum сверяется вручную. Каждый ключ принадлежит ровно одному списку: `project-change-owner` только глобальный.

## 9. Инварианты и одновременные запросы
**Инварианты.** Эти правила клиент видит всегда: ни один запрос и ни одна пара одновременных запросов не оставляет данные в нарушающем их состоянии.
- В проекте всегда есть минимум один owner, минимум одна доска и минимум один статус категории `done`.
- Номер задачи уникален в проекте и не переиспользуется; номера идут по возрастанию.
- Имя статуса, доски, направления и тега уникально в проекте (без учёта регистра); ключ проекта уникален; пара (проект, пользователь) — одно членство.
- Между двумя задачами не больше одной связи `blocks` в одном направлении, и цикла `blocks` нет.
- У архивного родителя нет неархивных подзадач.
- Порядок карточек внутри статуса однозначен: две карточки не занимают одну позицию, два чтения подряд отдают один порядок.
- Приглашение и запрос Telegram одноразовые: результат получает только один из одновременных запросов.
- После двух встречных `DELETE` статусов с `moveTo` (каждый переносит задачи в другой) у проекта остаётся хотя бы один статус, в том числе категории `done`; задачи не теряются: каждая остаётся в существующем статусе.
- У доски всегда хотя бы одна колонка: `PATCH` доски, который оставил бы колонку удаляемого статуса последней, получает 409 `board_would_be_empty`.
- Пользователь, удалённый из проекта, не остаётся исполнителем или ревьюером ни одной задачи проекта.

**Правило.** Если два одновременных запроса, каждый из которых по отдельности допустим, вдвоём нарушили бы инвариант, один из них успешен, а второй получает ответ с кодом из таблицы (не 500 и не успех с нарушением инварианта).

| Ситуация | Один запрос | Другой запрос получает |
|---|---|---|
| Смена категории или удаление двух статусов `done` (последний остаётся один) | успех | 409 `last_done_status` |
| Удаление двух последних досок | успех | 409 `last_board` |
| Смена роли, удаление участника, смена владельца, деактивация пользователя, из-за которых не остаётся owner | успех | 409 (`last_owner`, `owner_role_locked`, `already_owner` — по ручке) |
| Создание подзадачи под родителем, которого одновременно архивируют | либо подзадача создана и архивирована вместе с родителем, либо создание отклонено | 422 (`fields.parentId = archived`) |
| Добавление двух связей `blocks`, замыкающих цикл (A→B и B→A) | успех | 409 `link_cycle` |
| Перенос двух карточек в одну позицию | успех | успех или 409 `stale_position`; общих позиций у карточек нет |
| Создание двух задач в одном проекте | 201 с номером N | 201 с другим номером |
| Создание двух записей с одним уникальным именем (статус, доска, направление, тег, ключ проекта, логин) | 201 | 409 с кодом (`name_taken`, `project_key_taken`, `username_taken`) |
| Два одновременных `accept` одного приглашения, два опроса одного Telegram-запроса | 200 | 404 (`invitation_invalid` или `not_found`) |

**Критерий приёмки.** Скрипт отправляет по API такую пару запросов одновременно и повторяет 20 раз: ни разу не должно быть ответа 5xx, второго успеха там, где в таблице 409/422, и состояния, нарушающего инвариант (проверяется последующими `GET`: проект без owner, без `done`-статуса, без доски, с циклом `blocks`, с дублем номера или с подзадачей архивного родителя).

## 10. Списки и время ответа
Ручка, отдающая список или объект с вложенными списками, возвращает всё нужное экрану в том же ответе: статусы (`taskCount`, `boards`), направления и теги (`taskCount`), админские списки (`projectsCount`, `membersCount`), участники, задачи и подзадачи, карточки досок, история, комментарии, списания, уведомления, `links` и `urls` в `TaskDetail`. Клиенту не нужны дополнительные запросы на каждый элемент.

**Критерий приёмки** (для каждого пакета со списками): все перечисленные поля приходят в самом ответе списка (фронту не нужен отдельный запрос на строку); время ответа — ориентиры пакетов 5 и 6, а не условия приёмки.

## 11. Сквозное поведение пакетов
Эти эффекты нужны нескольким пакетам, и клиент должен видеть одинаковый результат, кто бы их ни вызвал.

| Поведение | Что видит клиент | Где проверяется |
|---|---|---|
| Смена статуса задачи (перенос карточки, перенос при удалении статуса) | `statusId`, позиция, `resolvedAt` (ставится при входе в `done`, сбрасывается при выходе), `updatedAt`, событие истории `status` | пакеты 3, 4, 6 |
| Запись в историю | все изменения одного запроса имеют общую `createdAt`; события не удаляются | пакеты 2–6 |
| Отметка «задача изменена» | `updatedAt` обновляется при изменении полей, тегов, статуса, исполнителя, архивации, связей, ссылок, комментариев; не обновляется списаниями, подпиской и перестановкой в колонке | пакеты 4, 5, 6, 7 |
| Автоподписки | автор, исполнитель, ревьюер, автор комментария и упомянутые подписаны ([b07](07-comments-worklogs-watches.md), раздел 4) | пакеты 4, 7 |
| Удаление участника из проекта | снят с исполнителя и ревьюера задач, подписки удалены, убран из базовых фильтров досок, история и комментарии сохранены | пакеты 2, 3, 4, 7 |
| Уведомления | создаются только после успешного завершения действия; сбой уведомления не ломает ответ действия | пакеты 4, 6, 7, 8 |

Комментарии-причины перевода появляются вместе с пакетом 6, публичные ручки комментариев — в пакете 7.

## 12. Повторы, неизвестные идентификаторы, курсоры, время
**Повторные запросы.** Ключа идемпотентности (`Idempotency-Key`) нет; фронт блокирует кнопку на время запроса. Что происходит при повторе того же запроса:

| Операция | Повтор |
|---|---|
| `POST` и `DELETE /tasks/:taskId/watch` | успех, 204, ничего не меняется |
| `POST /notifications/:id/read`, `POST /notifications/read-all` | успех, 204 |
| `PATCH`, `PUT` с теми же значениями | успех, 200; событий истории нет (пакет 4) |
| `POST /tasks/:taskId/move` в тот же статус и ту же позицию | успех, 200; `reason` игнорируется (причина не сохраняется, комментарий не создаётся) |
| `POST …/archive` | 409 `task_already_archived` |
| `POST …/restore` | 409 `task_not_archived` |
| `POST /admin/users/:id/deactivate` для деактивированного, `POST /admin/users/:id/activate` для активного | успех, 200, ничего не меняется |
| `DELETE /profile/telegram`, когда Telegram не привязан | успех, 204 |
| `DELETE` ресурса | 404 `not_found` |
| `POST` создания (задача, комментарий, списание, ссылка…) | не идемпотентно: создаётся ещё один объект. Исключения — сущности с уникальностью: 409 `name_taken`, `already_member`, `link_exists`, `username_taken`, `project_key_taken` |
| `POST /invitations/:token/accept`, `POST /auth/telegram/status` по закрытому запросу | 404 (`invitation_invalid` или `not_found`) |

**Неизвестный идентификатор в фильтре.** В фильтрах списка «Все задачи» (пакет 5) и досок (пакет 6) проверяется формат, а не существование. Значение не UUID (и не константа `me` / `none` там, где она допустима) — 422 (`fields.<параметр> = invalid`). Корректный UUID, которого нет в проекте (удалён, чужой), отбрасывается из списка значений; если значений не осталось, фильтр не применяется. Так не ломаются закладки со старым фильтром. `excludeId` в поиске — только формат.

**Страница за последней.** `page` больше числа страниц — 200, `items: []`, `total` как есть.

**Курсор.** В курсорных списках (комментарии — пакет 7, уведомления — пакет 8) параметр `before` — непрозрачная строка: клиент её не разбирает и берёт из поля `nextCursor` предыдущего ответа (`null`, если `hasMore = false`). Удаление записи, на которой остановилась предыдущая выдача (комментарий удалён, уведомление снесла очистка), не ломает «Показать ещё»: выдача продолжается с той же позиции без пропусков и повторов. Строка, которая не разбирается, — 422 (`fields.before = invalid`).

**Время.** Бэкенд считает «сегодня» и `isOverdue` по UTC. Дату списания фронт передаёт всегда (локальная дата пользователя; допустима до завтрашней по UTC, пакет 7). Фронт вправе пересчитать `isOverdue` по `dueDate` и локальной дате; даты без времени он не переводит через `Date`.

**Критерии приёмки.**
1. Таблица повторов: двойной `watch` и `unwatch`, `read` и `read-all` — 204 оба раза; `move` в ту же колонку с `reason` — 200, комментарий `status_reason` не создан; второй `archive` — 409, второй `restore` — 409; второй `DELETE` — 404; повторные `deactivate` и `activate` — 200; `DELETE /profile/telegram` без привязки — 204; два `POST` комментария — два комментария; второй `accept` и второй `POST /auth/telegram/status` по закрытому запросу — 404.
2. Фильтры по неизвестным идентификаторам: проверка в критериях пакетов 5 и 6.
3. Курсор: проверка в критериях пакетов 7 и 8 (в том числе удаление записи, на которой остановилась выдача).
4. `POST /tasks/:taskId/worklogs` с `date`, равной завтрашней дате UTC, проходит; послезавтрашней — 422 (`fields.date = in_future`); `dueDate` и `date` отдаются строкой `YYYY-MM-DD` без времени.
5. Каждый ответ содержит `X-Request-Id` и `Referrer-Policy: no-referrer`; в теле 5xx `error.requestId` равен заголовку; заголовок, присланный клиентом, возвращается как есть.
6. Каждая операция из `openapi.yaml` объявляет ответы 400 и 500; тело любого 4xx и 5xx имеет формат `ErrorResponse` с `code` из перечня `ErrorCode`.

## 13. Рекомендации (необязательно)
Разработчик бэкенда вправе выбрать иначе; ниже — то, что авторам ТЗ кажется разумным.

- **СУБД.** PostgreSQL ≥ 14. Схема, миграции и сид создаются вместе с таблицами пакета; индексы, уникальные ключи и политика внешних ключей — в [13-data-model-and-permissions.md](../13-data-model-and-permissions.md), раздел 7. Нужен скрипт сброса и пересоздания базы для разработки. Переменные `DATABASE_URL`, `LOG_LEVEL`, `NODE_ENV` — по выбранному стеку.
- **Пароли и токены.** Пароли — argon2id (или bcrypt с cost ≥ 12). Секретные токены (приглашения, сессии, Telegram-запросы) хранить только в виде хеша, генерировать криптостойким генератором, минимум 128 бит. Токен Telegram-запроса — 16 байт в base64url без `=` (22 символа), чтобы он проходил в `?start=` и `callback_data`.
- **Логи.** Структурные (JSON, одна запись на строку), уровень задаёт `LOG_LEVEL` (`debug` | `info` | `warn` | `error`), в них `X-Request-Id`; пароли, токены и cookie в логи не попадают, токены в адресе (`/invitations/<token>`, `?token=`) маскируются; тело `POST /auth/telegram/status` не пишется. Swagger UI по адресу `/api/docs` — вне продакшена.
- **Конкурентность.** Проверка и запись в одной транзакции под блокировкой, порядок взятия блокировок один и тот же — проект, статус, родительская задача, задача.

| Что защищаем | Блокировка | Где |
|---|---|---|
| «Последний статус `done`», «последняя доска» | `SELECT … FOR UPDATE` строки проекта | [пакет 3](03-dictionaries-and-templates.md) |
| «Минимум один owner» | `SELECT … FOR UPDATE` строки проекта | [пакет 2](02-projects-members-permissions.md), [пакет 1](01-accounts-and-sessions.md) |
| Создание подзадачи и архивация родителя | `FOR SHARE` строки родителя при создании подзадачи, `FOR UPDATE` при архивации родителя | [пакет 4](04-tasks-core.md) |
| Проверка цикла `blocks` и вставка связи | `pg_advisory_xact_lock` по `projectId` | [пакет 5](05-links-search-list.md) |
| Расчёт `rank` при создании и переносе | `FOR UPDATE` строки статуса | [пакет 6](06-boards-and-move.md) |
| Номер задачи | атомарный `UPDATE … SET taskSeq = taskSeq + 1 RETURNING` | [пакет 4](04-tasks-core.md) |

  Нарушение уникального ограничения или внешнего ключа при гонке перехватывать одним фильтром и превращать в 409 с кодом по имени ограничения, а не отдавать 500.
- **Без N+1.** Связанные данные (исполнитель, автор, теги, счётчики, суммы времени) подгружать пакетно (`JOIN` или `WHERE id IN (…)`), чтобы число SQL-запросов на один запрос API не зависело от числа элементов в ответе. Проверить можно счётчиком запросов драйвера или ORM.
- **Внутренние сервисы.** Общие операции вынести один раз и вызывать из пакетов: `rankBetween(a, b)` (ранг между соседями, перенумерация при длине больше 64; пакет 4, алгоритм — [пакет 6](06-boards-and-move.md), рекомендации), `applyStatus(task, statusId, position, actor)` (`statusId`, `rank`, `resolvedAt`, `updatedAt`, история), `recordHistory(taskId, actor, events)`, `touchTask(taskId)`, `ensureWatching(taskId, userIds)` (пакет 7), `removeMemberEffects(projectId, userId)`, `publishDomainEvent(event)` — публикация после коммита. До готовности пакета с реализацией в зависимых пакетах стоит заготовка с тем же поведением.
- **Курсор.** Устройство курсора: base64url от пары (`createdAt`, `id`) элемента, с которого продолжается выдача.
- **Тесты.** Интеграционные тесты бэкенда — на усмотрение разработчика; для критерия раздела 9 удобен скрипт с параллельными запросами.
- **Конфигурация и Telegram.** Файл `.env.example` со всеми переменными без реальных значений; бота заводить на каждое окружение отдельно (свой `TELEGRAM_BOT_TOKEN`), в режиме `polling` один токен обслуживает один экземпляр (иначе `getUpdates` отвечает 409). Где своего бота нет, `TELEGRAM_DRY_RUN=true`: сообщения не отправляются, а пишутся в журнал приложения; подтверждение входа и привязки доводить до `confirmed` поддельными `update` через `POST /telegram/webhook`. `PORT`, `DATABASE_URL`, `LOG_LEVEL` — по выбранному стеку.
- **Тестовые данные.** `DEV_SEED=true` создаёт пользователей с ролями и проекты для фронтенда (пароль — `DEV_SEED_PASSWORD`), повторный старт не создаёт дублей. Составы по пакетам — в разделах «Тестовые данные».
