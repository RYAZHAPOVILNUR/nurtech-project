# Task-manager: границы проекта и скоуп (v3)

Живой документ: правится по ходу макетов, проектирования API и оценки трудозатрат.

## Контекст
Учебный проект с «коммерческим» процессом: 12–14 учеников (в плане 13), Angular 21 + Taiga UI + ngrx-signals, без тестов, срок 8 недель. Ревью и мердж делает ментор. Бэкенд пишет отдельный разработчик (AI-агент), его сложность почти не стоит; узкое место — фронт и нагрузка на ревью. Главное: **проект — это доска задач**, а не набор фич для менеджеров. Layout и вход по паролю делает ментор.

## Принятые решения

### Доступ и аккаунты
| Область | Решение |
|---|---|
| Права | Бэкенд отдаёт список ключей разрешений, повторяющих действия/эндпоинты, через дефис: `project-create`, `task-create`, `task-move`. Директива `*appCan` принимает массив ключей (any/all). В Swagger у каждой ручки в описании указан контролирующий ключ (`x-permission` + строка в `description`). Тип `Permission` на фронте генерируется из `x-permission`. 4 системные роли проекта (owner/admin/member/viewer) сидятся миграцией; кастомные роли — после релиза. Глобальные ключи системного администратора приходят в `GET /auth/me` (см. [10-account-and-admin.md](10-account-and-admin.md)). |
| Свои и «чужие» сущности | `GET /projects/:id/me` возвращает `{ userId, role, permissions }`. У комментария и worklog есть `authorId`: своё можно править/удалять (фронт сравнивает `authorId` с `userId`, бэкенд проверяет то же). «Чужое» (модерация комментариев, чужие worklog) — хелпер `isProjectAdmin` (роль owner/admin), отдельных ключей нет. При появлении кастомных ролей хелпер заменить флагом с бэкенда. |
| Изоляция | **Проект — единственная граница доступа.** Все участники проекта видят все его доски. Для изоляции создаётся отдельный проект. |
| Глобальные роли | Системный администратор создаёт проекты и приглашает людей в систему. Участников в проект добавляет owner/admin проекта из числа уже приглашённых. |
| Вход | По приглашению. При принятии приглашения: установить пароль или продолжить через Telegram. Вход через Telegram-бота: фронт получает `deepLink`, открывает его, раз в 2 с опрашивает статус, пользователь подтверждает в боте; для фронта — одна кнопка и конечный автомат (waiting → confirmed / expired). В профиле можно привязать второй способ. Сессия — httpOnly cookie на 7 дней с продлением при активности (предел 30 дней), число неудачных попыток входа ограничено ([backend/01](backend/01-accounts-and-sessions.md), разделы 2 и 4). |
| Аккаунт | Имя, уникальный `username` (для @упоминаний; человек выбирает сам при принятии приглашения, при входе через Telegram предлагается из Telegram; потом не меняется), способы входа, статус (активен/деактивирован). Аватар — инициалы на цветном фоне. Почты нет: «забыл пароль» = системный администратор выдаёт новую ссылку. Пользователи не удаляются, а деактивируются. |
| Проект | Название, ключ (префикс `PROJ`), описание, шаблон (Dev team / Simple). Владельца меняет только системный администратор; архивации проекта в первой версии нет (после релиза). |

Подробно роли, матрица ключей, правила и сценарии: [02-scenarios-and-permissions.md](02-scenarios-and-permissions.md). Системный администратор управляет проектами и людьми, но содержимое проектов видит только как участник.

### Задачи
| Область | Решение |
|---|---|
| Тип | Task / Bug / Subtask. Иерархия: Task/Bug → Subtask. Эпиков и item type нет (вырезаны ради сроков, см. «Не входит»): группировка и классификация — теги. |
| Приоритет | Фиксированный список Low / Medium / High / Critical. |
| Направление (subsystem) | Справочник проекта с полным CRUD. Значения по умолчанию задаёт шаблон проекта: «Dev team» — Frontend / Backend, «Simple» — пусто (поле скрыто, пока нет значений). В UI поле называется «Направление» (в API `subsystem`). Удаление используемого значения — с переназначением. |
| Модель (предварительно) | Окончательную модель определит проектирование API. Состав: название, описание (markdown), type, статус, приоритет, исполнитель (один), ревьюер (один), направление, теги, parent (только у подзадач), срок («К дате»), оценка (время; у родителя дополнительно показывается сумма по подзадачам), связи («Блокирует» / «Заблокирована», только в рамках проекта), ссылки (список URL с названием: merge-request, документы), подписки. Системные поля: key (`PROJ-123`), reporter, createdAt, updatedAt, resolvedAt (при переходе в статус категории done), сумма worklog, признак архивации. Удаление задачи — архивация. Resolution нет, вместо него статусы Done / Cancelled. Шаблон описания для Bug подставляется в редактор. |
| Время | Оценка во времени + worklog (дата, длительность, комментарий) как в YouTrack. Ввод в формате `2h 30m`. |
| Комментарии | Плоские. «Ответить» вставляет `@username` в редактор; упоминание создаёт уведомление (фронт отправляет `mentions: [userId]`). Редактор: поле markdown + превью. |
| История | Лог изменений: статус, исполнитель, ревьюер, приоритет, type, направление, теги, срок, оценка, связи, ссылки (кто, когда, было → стало). Комментарии и worklog в лог не дублируются. |
| Уведомления | События: назначили исполнителя/ревьюера; @упоминание; комментарий, смена статуса, исполнителя и ревьюера у задачи, на которую подписан (семь типов, [11](11-navigation-and-notifications.md)); смена приоритета, срока и других полей не уведомляет. Автоподписка: автор, исполнитель, ревьюер, автор комментария и упомянутые в нём ([04-task-card.md](04-task-card.md), «Подписка»); остальные — звёздочкой. Колокольчик со счётчиком (polling), список, «прочитано». Те же события — в Telegram-бот. Настроек нет, кроме включения Telegram. |
| Вложения | После релиза (Q-05): ТЗ-пакета, ручек и макетов нет, ключи `attachment-*` в резерве. При возврате обязательны требования безопасности: лимит размера, белый список MIME с проверкой сигнатуры, `storageKey` генерирует сервер, скачивание только с проверкой членства в проекте, `Content-Disposition: attachment`, `nosniff`, SVG и HTML не отдаются inline (C-03). |

### Доски и статусы
| Область | Решение |
|---|---|
| Модель | **Один workflow на проект, несколько досок над ним.** Доска = фильтр + набор колонок; колонка = ровно один статус. Статусы и доски создаёт шаблон проекта; редакторы статусов и досок — после релиза (Q-05). |
| Шаблоны | «Dev team»: доски **Планирование** (Backlog, PBR, Plan, To do) и **Разработка** (To do, Reopened, In progress, In review, In test, For release, Blocked, Done). Статус To do виден на обеих. «Simple»: To do / In progress / Done / Cancelled, одна доска. Категория done содержит Done и Cancelled. Колонки Cancelled в Dev-шаблоне нет: статус ставится в карточке, отменённые задачи видны в «Все задачи» и по ссылке «все закрытые →». Новая задача создаётся со статусом первой колонки текущей доски (из списка и карточки — с первым статусом проекта), статус можно выбрать в диалоге. |
| Перенос | DnD внутри доски. Перетащил карточку в To do на планировании — статус стал To do, задача сразу видна на доске разработки и остаётся на планировании. Статус меняется и в панели полей. DnD двух досок рядом не делаем. Запрос `POST /tasks/:id/move {statusId, prevId, nextId}`: фронт шлёт соседей, которых видит пользователь (даже если между ними есть скрытые фильтром или архивные задачи), порядок считает бэкенд. |
| Причина | Флаг `requiresReason` на статусе. По умолчанию у Cancelled и Blocked; у Reopened необязательна. Диалог при переносе (Blocked) или при смене статуса в карточке (Blocked, Cancelled), причина сохраняется комментарием. |
| Blocked | Колонка Blocked — ручной статус; бейдж «заблокировано» — автоматический по связям. |
| Направления на досках | Шаблон создаёт «Планирование» и «Разработку»; доски «Frontend» и «Backend» (та же доска с фильтром по направлению) добавляет ментор, редактора досок в первой версии нет. Swimlanes нет. |
| Подзадачи | Подзадачи — отдельные карточки с бейджем родителя. |
| Done | Показываются закрытые за последние N дней (по умолчанию 14) с подписью и ссылкой «все закрытые →». Ссылка открывает «Все задачи» с фильтром статуса по всем статусам категории done и с теми же фильтрами, что сейчас на доске. |
| Фильтры | Структурные фильтры с выбором нескольких значений (статус, исполнитель, ревьюер, приоритет, тип, направление, теги) + поиск по названию и ключу (по ключу — только запрос вида номера: `12`, `-12`, `KEY-12`; иначе по названию). В «Исполнителе» и «Ревьюере» первым пунктом «Я» (это заменяет быстрые чипы «на мне»); «Архивные» — пункт в фильтре статуса, только admin/owner. Тот же компонент задаёт фильтр доски. Языка запросов нет. |
| Карточка на доске | Одна компактная версия; двойной клик открывает карточку задачи, одинарный выделяет; ключ задачи — ссылка, одинарный клик по ключу тоже открывает. Значок типа, ключ, приоритет, название (до 3 строк), теги (показываются два, остальные «+N»), бейджи «родитель» и «заблокировано», «К дате» (красным и с иконкой часов при просрочке), аватар исполнителя. Описания, количества вложений и комментариев на карточке нет. |
| Realtime | В ядре: polling + refetch на focus; при перетаскивании polling приостанавливается; перенос — optimistic update с откатом. SSE — после релиза (при возврате: проверка cookie и Origin при подключении, фильтрация каждого события по текущему членству, закрытие потока при выходе, деактивации и удалении из проекта — C-17). |

### Страницы
Доски, список задач (таблица, он же результаты поиска), карточка задачи, настройки проекта (общие, направления, теги), участники, профиль, администрирование (пользователи, приглашения, проекты), пустой экран «Вас ещё не добавили в проекты». Интерфейс только русский.

**Карточка задачи (как в YouTrack):** шапка (ключ, название, звёздочка), описание, связи и подзадачи, вкладки «Комментарии / Время / История» и теги под названием, панель полей (статус, приоритет, type, исполнитель, ревьюер, направление, срок, оценка, затрачено).

### UX
- Верхняя панель без вкладок: переключатель проектов, меню проекта (⚙: «Участники» для всех, «Настройки проекта» для owner/admin), уведомления, профиль (там же «Администрирование» для системного админа).
- Навигация и уведомления: [11-navigation-and-notifications.md](11-navigation-and-notifications.md); общие правила интерфейса: [12-ui-rules.md](12-ui-rules.md).
- Подробно доски: [07-boards-page.md](07-boards-page.md); настройки проекта: [08-project-settings-page.md](08-project-settings-page.md); участники: [09-members-page.md](09-members-page.md); вход, приглашение, профиль и администрирование: [10-account-and-admin.md](10-account-and-admin.md).
- Переключатель видов рядом с поиском: разделы «Доски» (Планирование, Разработка…) и «Списки» (Все задачи); открывается последний использованный вид.
- «Все задачи» — список всех неархивных задач проекта, включая бэклог, с серверной пагинацией; в строках Task и Bug, подзадачи раскрываются: [06-all-tasks-page.md](06-all-tasks-page.md).
- Быстрого создания в колонке нет; «+ Задача» — диалог со всеми полями карточки для Task, Bug и Subtask (у Subtask родитель обязателен), после создания открывается карточка: [05-create-task-dialog.md](05-create-task-dialog.md).
- Одинарный клик по карточке на доске или по строке в списке выделяет её, двойной клик (или Enter у выделенной, или одинарный клик по ключу) открывает задачу боковой панелью поверх страницы; адрес вида получает `?task=KEY`. Адрес `/p/PROJ/tasks/PROJ-123` — входная ссылка (Telegram, чат): редирект на последний использованный вид проекта с `?task=`.
- Фильтры и открытая задача (`?task=KEY`) в query-параметрах; последний набор фильтров между сессиями не запоминается (Q-05, I-19), запоминается только последний вид.
- Автосохранение полей панели полей (при ошибке общее сообщение приложения, см. [12-ui-rules.md](12-ui-rules.md), «Язык и термины»); описание и комментарии — кнопкой «Сохранить».
- Недоступные действия скрываем; viewer не может перетаскивать.
- Выбор исполнителя и ревьюера с поиском, «Назначить на меня».
- «Списать время» в карточке, дата — сегодня, комментарий необязателен; индикатор «затрачено / оценка».
- Для каждой страницы: пусто / загрузка / ошибка.
- Адреса: `/p/PROJ/board/:id`, `/p/PROJ/tasks` (список); открытая задача — `?task=PROJ-123` у любого вида; `/p/PROJ/tasks/PROJ-123` — входная ссылка с редиректом на вид с `?task=`.

## Не входит
Эпики (макеты и описание страницы лежат в [archive/epics](archive/epics)), item type, спринты, milestone, story points, кастомные поля, кастомные роли и типы, права на отдельные доски, правила переходов workflow, swimlanes, DnD между досками, язык запросов, WYSIWYG-редактор, мобильная версия доски, загрузка аватаров, Gantt, импорт/экспорт CSV, исходящие вебхуки, интеграция с Git (кроме поля ссылок), связи между проектами, страница «Мои задачи». Отчёты и дашборды — после релиза, если останется время.

Решено вынести за первую версию (Q-05, Q-23): SSE, личные сохранённые фильтры, редакторы статусов и досок, вложения, архивация проекта (раздел «Архив», баннер, возврат), связи «связана» и «дубликат», журнал безопасности, точные числа в окне удаления участника, служебное поле каскада архивации задач.

## Приоритеты
- **Ядро:** вход по приглашению (пароль) и через Telegram, проекты/участники/роли (admin = owner, кроме смены владельца), задачи и поля, справочники проекта (направления и теги; статусы и доски создаёт шаблон), доски и DnD, доска планирования, связи «Блокирует» / «Заблокирована», комментарии с @, история, оценка и worklog, структурные фильтры и поиск, список задач, уведомления в приложении и Telegram-бот, подписки.
- **Важного нет:** всё, что раньше было «если успеваем», вынесено после релиза. Ментор: «успеть» всё необязательно, после обучения доделать можно с агентами.
- **После релиза:** SSE, личные сохранённые фильтры, редакторы статусов и досок (сортировка статусов — кнопками ↑/↓), вложения, архивация проекта, связи «связана» и «дубликат», эпики, item type, отчёты, кастомные поля и роли, milestone, права на доски, тёмная тема, сообщение «Отменить» после DnD, массовые операции.
- Мобильная версия: доска только десктоп; таблицу и карточку, возможно, адаптируем — решим по дизайну.
- **Линия отсечения** (режем снизу вверх): Telegram-бот → Telegram-вход. Решение по линии принимается на КТ1 (конец недели 3) и КТ2 (конец недели 5), см. «Этапы». Линия короткая сознательно: всё остальное «важное» уже вынесено после релиза (≈ 69 ч из прежнего плана: вложения 25 и редакторы статусов и досок 44; плюс ≈ 17 ч упрощений Q-23 и 4 ч двойного учёта переключателя видов), а запас плана даёт буфер, а не линия.

## Процесс
- Ветки `dev` + `main` («прод»). Ученики мержат в dev после перекрёстного ревью учеников, `main` ведёт только ментор и релизит в него раз в неделю. Размер PR плавающий, но как можно меньше строк. Тесты не пишем.
- Задачи одиночные, PR по одной задаче. Единица оценки — час ученика (не опытного разработчика). «Ученико-неделя» — одна норма: 7 ч в неделю, из них ≈ 5,6 ч чистой работы после онбординга и ревью; задача не больше 6 ч и помещается в одну ученико-неделю. Пункты оценок крупнее 6 ч заранее разбиваются на задачи: панель полей 24 ч — ≈ 8 задач по 3 ч, drag&drop на доске 24 ч — ≈ 5 задач по 5 ч.
- Контракт API — OpenAPI; до готовности пакета бэкенда страница собирается на константах, типизированных `src/app/api/generated` (фикстуры `*.fixture.ts` лежат рядом с компонентом, не в сервисах и не в интерцепторах); после приёмки пакета подключается сервис. График пакетов — ориентир разработчику бэкенда, а не обязательный срок (Q-02, Q-40; [backend/00](backend/00-conventions.md), раздел 1, и «Этапы» ниже).
- Ритм: дейлики, еженедельное планирование (перенос задач в To do).
- Ревью: перекрёстное ревью учеников перед ментором, небольшие PR (строк как можно меньше, жёсткого лимита нет — Q-08), definition of done у задач. Скелет проекта (структура папок, правила сторов, API-клиент) делает ментор.

## Этапы, часы и контрольные точки
Часы — ученика (Q-01), взяты из разделов «Оценка трудозатрат фронта» документов 04–11 (источник каждой цифры — колонка «Источник»); при изменении оценок таблицы пересчитываются вручную. Часы ментора в ёмкость учеников не входят, но указаны отдельно. Каркас ментора (репозиторий, CI, API-клиент, shell и маршруты, README с примерами) в оценках не учтён: он идёт до старта учеников (неделя 0).

**Правила плана.**
- Список задач — только в этапе 4; его компонент фильтров делается первой задачей этапа 3 вместе с диалогом причины (общие для досок и списка). Статусы и доски — из шаблона проекта. Telegram — в ядре, отсекается последним (этап 7).
- В неделю 1 студенты делают презентационные компоненты и страницы без данных (сквозные работы), каркас с данными — у ментора с недели 0. Общие поля карточки (панель полей) идут отдельным эпиком на неделю раньше остальных частей карточки.
- Правила «пакет готов за неделю до страницы» нет (Q-02, Q-40): график пакетов — ориентир разработчику бэкенда ([backend/00](backend/00-conventions.md), раздел 1); пока пакета нет, страница работает на константах, после приёмки пакета подключается сервис.
- **КТ1 (конец недели 3):** можно войти, пригласить пользователя, создать проект и переключаться между проектами; готова панель полей карточки. Контрольная точка плана: выработка = закрытые часы / плановые часы; оценки пересчитываются на факт. При выработке ниже 85% сразу снимается Telegram-бот.
- **КТ2 (конец недели 5):** рабочая доска с drag&drop, карточка с полями, участники, настройки проекта. При выработке ниже 90% снимается Telegram-вход (этап 7 ещё не начат).
- **КТ3 (конец недели 7):** полный цикл задачи — создание, комментарии, время, история, связи, список, уведомления.
- **КТ4 (конец недели 8):** релиз в `main`.
- Пороги выработки 85% и 90% — предложение плана, ментор может изменить.

## Этапы планирования (итеративно)
1. Пользовательские сценарии по ролям (системный админ, owner/admin, member, viewer), граничные случаи.
2. Постраничная проработка: назначение, состояния, действия и права, схематичный макет, API-ручки.
3. Оценка трудозатрат и рентабельности по страницам/фичам; сдвиг линии отсечения.
4. ТЗ бэкенда пакетами, по графику пакетов (ориентир, Q-40).
5. Бэклог в tree.taiga.io: эпики Taiga = страницы/фичи (это инструмент планирования команды, в самом продукте эпиков нет), задачи ≤ «ученико-недели» (шаблон карточки, разбиение, импорт скриптом по REST API Taiga и DoD — в [15-backlog.md](15-backlog.md); ревьюер и оценка — кастомные атрибуты).

После каждой стадии — сверка и правки этого документа.

## Риски
Объём: 12–14 учеников (в плане 13) по 6–8 ч в неделю (в плане 7): ≈ 730 ч полной ёмкости за 8 недель, ≈ 580 ч чистой после онбординга и ревью (≈ 20%); план занимает ≈ 490 ч, буфер ≈ 16%. Telegram в ядре повышает риск. Реестр: риск · вероятность · влияние · меры. Продукт — не копия YouTrack (там главное язык запросов, кастомные поля, скриптовый workflow), а доска + карточка + справочники, ближе к Linear/Trello+; универсальность для не-IT ограничена отсутствием кастомных полей и ролей.

| Риск | Вероятность | Влияние | Меры |
|---|---|---|---|
| Перегрузка недель 2 и 4 (этапы идут одновременно) | средняя | высокое | Этапы растянуты по неделям: пик 93% чистой ёмкости (недели 2–3 и 7), КТ1 в конце недели 3 (см. «Этапы») |

| Учеников меньше плана или они уходят (отток) | средняя | высокое | Планировать сценарии на 10, 14 и 20 человек; ядро собрано так, чтобы отдельную страницу мог закончить один человек |
| Пакеты бэкенда не готовы к сроку | средняя | высокое | Страницы на константах до готовности пакета; график пакетов по неделям — ориентир в [backend/00](backend/00-conventions.md), раздел 1; пакет 5 готов вместе с пакетом 6 |
