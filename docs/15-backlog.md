# Бэклог в Taiga: шаблон карточки, разбиение, импорт, DoD

Связан с [01-scope.md](01-scope.md) (раздел «Процесс» и «Этапы»), документами страниц [04–11](04-task-card.md) (оценки трудозатрат и разделы «Приёмка») и [12-ui-rules.md](12-ui-rules.md). Бэклог ведётся в tree.taiga.io; это инструмент планирования команды, в самом продукте эпиков нет.

Решения: способ импорта — Q-28 (скрипт по REST API Taiga), процесс — Q-08 (ментор оформляет сам). Источники полей Taiga:
- **doc-api** — `github.com/taigaio/taiga-doc`, каталог `api/` (файлы `.adoc`), сверено при составлении документа;
- **docs.taiga.io** — `docs.taiga.io/api.html` (общий справочник API);
- **community** — `community.taiga.io` (ответы команды Taiga, не документация).

Всё, что не подтверждено файлом doc-api или docs.taiga.io, помечено **«проверить»**: перед использованием проверяется на живом `tree.taiga.io` (или в Swagger/справочнике API) и результат записывается в таблицу.

## 1. Соответствие сущностей

| Что у нас | Что в Taiga | Источник |
|---|---|---|
| Страница или фича (карточка задачи, доски, участники …) | Epic | docs.taiga.io (эпики); привязка US к эпику — `POST /api/v1/epics/{id}/related_userstories`, **проверить** (файл doc-api для этой ручки на момент составления не найден) |
| Задача ученика (одна задача — один PR, ≤ 6 ч) | User Story | doc-api `api/user-stories/create.adoc` |
| Шаг внутри задачи | Task (с `user_story`) | doc-api `api/tasks/create.adoc` |

## 2. Шаблон карточки

### 2.1. Поля User Story

| Что хотим хранить | Поле Taiga | Источник | Статус |
|---|---|---|---|
| Заголовок вида «[Страница] глагол + результат» | `subject` (обязателен вместе с `project`) | doc-api `user-stories/create.adoc` | подтверждено |
| Контекст, что сделать, что не входит, чек-лист приёмки | `description` | там же | подтверждено |
| Метки: страница, front/back, `shared-component`, `mentor-skeleton`, `easy`/`medium` | `tags` (массив строк) | там же | подтверждено |
| Исполнитель | `assigned_to` (id пользователя) | там же | подтверждено |
| Неделя | `milestone` (id; `Неделя N`) | там же | подтверждено; что milestone = «неделя», решение команды; сами milestone создаёт скрипт (раздел 5, шаг 3) |
| Блокировка | `is_blocked` + `blocked_note` | там же | подтверждено |
| Ментор-подписчик | `watchers` (массив id) | там же | подтверждено |
| Статус | `status` (id) | там же | подтверждено |
| Картинка макета | вложение: `object_id`, `project`, `attached_file`, необязательные `description` и `is_deprecated` | doc-api `user-stories/create-attachment.adoc` | подтверждено; путь ручки — **проверить** |
| Ревьюер | кастомный атрибут «Ревьюер» | doc-api `userstory-custom-attributes/create.adoc` | атрибут создаётся (поля `project`, `name`, необязательные `description`, `order`); **тип «выпадающий список» и его значения — проверить**: в этом файле поля `type` нет, в community перечислены типы «текст, многострочный, rich text, дата, URL, выпадающий список, чекбокс, число» (`community.taiga.io/t/customisation-for-your-projects/127`); мультивыбор не поддерживается (`community.taiga.io/t/add-multi-select-field-type/1016`) |
| Оценка, ч | кастомный атрибут «Оценка, ч», тип «число» | community …/127 | **проверить** (тип); шкала `points` в часах в документации не подтверждена, поэтому `points` не используем |
| Документ (`docs/NN-page.md §X`) | кастомный атрибут «Документ», тип URL или текст | community …/127 | **проверить** (тип) |
| Макет (`docs/wireframes/<page>/<file>.svg`) | кастомный атрибут «Макет», тип URL или текст | community …/127 | **проверить** (тип) |
| Пакет бэкенда (1–8, готов / ждёт пакет) | кастомный атрибут «Пакет бэкенда», выпадающий список 1–8 | community …/127 | **проверить** (тип и значения) |
| Значения атрибутов | `PATCH /api/v1/userstories/custom-attributes-values/{id}` (для шагов — `/api/v1/tasks/custom-attributes-values/{id}`), тело `{ "attributes_values": { "<id атрибута>": <значение> }, "version": <текущая> }`; `version` берётся из `GET` того же ресурса | doc-api `api/generated/user-stories-custom-attributes-values-patch-cmd.adoc` | подтверждено по сгенерированному примеру; после записи перечитать значения и сверить |

Поля US из doc-api, которые **не используем**: `points`, `backlog_order`, `kanban_order`, `sprint_order`, `client_requirement`, `team_requirement`, `is_closed` (закрытие идёт статусом).

### 2.2. Поля Task (шаги внутри карточки)

Подтверждено doc-api `tasks/create.adoc`: `project`, `subject` (обязательны), `user_story`, `description`, `tags`, `assigned_to`, `status`, `is_blocked`, `blocked_note`, `milestone`, `watchers`. Поле `points` у Task отсутствует: оценка шага — только кастомным атрибутом задач «Оценка, ч» (**проверить**: атрибуты у Task заведены отдельным ресурсом `task-custom-attributes`, каталог есть в doc-api, поля не сверены). Остальные поля Task (`us_order`, `taskboard_order`, `is_closed`, `is_iocaine`, `external_reference`) не используем.

### 2.3. Шаблон `description`

```text
Контекст: …
Документ: docs/NN-page.md §X   Макет: docs/wireframes/<page>/<file>.svg
API: METHOD path (x-permission: …)   Пакет бэкенда: N (готов / ждёт пакет N)
Зависит от: #ref
Что сделать: …
Не входит: …
Приёмка (сид DEMO): копия пунктов из раздела «Приёмка» документа страницы
- [ ] Дано … Действие … Ожидаю …
- [ ] Под eva_viewer: недоступное скрыто
- [ ] Загрузка / пусто / ошибка (Повторить)
- [ ] Ошибка <код> показана как …
Оценка: N ч (≤ 6)
DoD: см. раздел 6
```

Правила заполнения:
- Заголовок: «[Карточка] Автосохранение полей: очередь и откат». Страница в квадратных скобках — для поиска.
- «Приёмка» не придумывается заново: берутся пункты из раздела «Приёмка» документа страницы (ID вида `T2.4`), чтобы ревьюер проверял то же, что написано в документе.
- Метки: страница (`card`, `board`, `all-tasks`, `settings`, `members`, `account`, `admin`, `nav`), слой (`front`/`back`), `shared-component`, `mentor-skeleton`, сложность `easy`/`medium`.
- Ссылки на документ и макет всегда относительные от корня репозитория.

## 3. Правила разбиения

1. **Одна задача — один PR, ≤ 6 ч** ученика ([01](01-scope.md), «Процесс»): помещается в одну «ученико-неделю» (7 ч, из них ≈ 5,6 ч чистой работы). Оценка — час ученика, не опытного разработчика.
2. Пункт оценки из разделов «Оценка трудозатрат фронта» страниц 04–11 больше 6 ч режется до постановки. Критерий готовности разбиения — ни одна карточка не больше 6 ч, сумма частей равна исходной оценке (допуск ±1 ч).
3. Резать по **поведению**, а не по слою: каждая часть даёт проверяемый результат из раздела «Приёмка». Нельзя резать так, чтобы часть нельзя было проверить без другой (допустимо — через моки).
4. Общие компоненты (панель полей, фильтры, диалог причины) идут **отдельными карточками раньше потребителей** и помечаются `shared-component`; сигнатуры (входы, выходы, `ControlValueAccessor`) фиксирует ментор до начала карточек.
5. Скелет и сервисы, которые слабому ученику не по силам, делает ментор (`mentor-skeleton`), его часы в ёмкость учеников не входят: `BoardStore.move()` с оптимистичным обновлением и откатом, `neighborsAt(column, index)` (сигнатура), общий `TelegramAuthFlow` для входа, приглашения и привязки (E-18), сессия и вход по паролю ([01](01-scope.md)).
6. Карточка с зависимостью от бэкенда указывает «Пакет бэкенда: N» и, пока пакет не готов, собирается на константах, типизированных сгенерированным клиентом ([backend/00](backend/00-conventions.md), раздел 1).
7. Если при работе выяснилось, что не влезает в 6 ч, ученик не растягивает PR: делает завершённую часть, остальное — новая карточка, ментору пишется причина.

## 5. Импорт бэклога в Taiga (Q-28)

В Taiga **нет CSV-импорта** user story: команда Taiga ответила, что поддерживается перенос проекта между инстансами (`community.taiga.io/t/import-from-csv/1153`); импортёры — Trello, GitHub, Jira, загрузка дампа `POST /api/v1/importer/load_dump` (docs.taiga.io/api.html). Поэтому по ответу на Q-28 выбран вариант **а): скрипт по REST API Taiga**.

**Что делает скрипт** (для бэклога MVP скрипт был написан и выполнен разово, в репозитории не хранится; описание ниже — для повторного импорта полной версии):
1. Читает файл карточек `docs/backlog/cards.yaml` (YAML; заполняет ментор по разделам «Оценка трудозатрат фронта» страниц 04–11 и разбиениям из раздела 4; в файл попадают только готовые к постановке карточки). Поля карточки: `key` (уникальный, например `board-dnd-2`), `epic` (страница или фича), `subject`, `hours`, `week` (одно число 1–8; при разбиении пункта, растянутого на несколько недель, части раскладываются по неделям диапазона), `tags`, `doc` (`docs/NN-page.md §X`), `wireframe`, `api`, `package` (1–8), `acceptance[]` (id пунктов «Приёмки»), `steps[]` (шаги внутри карточки). Проверка: сумма часов карточек страницы равна сумме её позиций оценки ±1 ч.
2. Авторизуется в API; токен берёт из переменной окружения, в репозиторий и в логи не пишет (способ получения токена — docs.taiga.io/api.html, **проверить**).
3. Один раз: создаёт 8 milestone `Неделя N` (`POST /api/v1/milestones`: `project`, `name`, `estimated_start`, `estimated_finish`; даты старта недель задаёт ментор) и создаёт кастомные атрибуты US и Task (Ревьюер, Оценка ч, Документ, Макет, Пакет бэкенда; `POST` на `userstory-custom-attributes`, поля `project`, `name`, `description`, `order`; тип задаётся и проверяется вручную в интерфейсе — **проверить**, можно ли задать тип через API) и запоминает их id.
4. Для каждой страницы создаёт Epic (поля Epic — **проверить**) и привязывает US через `related_userstories` (**проверить**).
5. Для каждой карточки: `POST /api/v1/userstories` (`project`, `subject`, `description`, `tags`, `milestone`, `status`), затем `PATCH` значений атрибутов (тело `attributes_values` и `version`, раздел 2.1), затем шаги — `POST /api/v1/tasks` (`user_story`).
6. Режим `--dry-run` печатает, что будет создано, без запросов на запись. Повторный запуск не создаёт дубликатов: основной способ — локальный файл соответствий «ключ карточки → id в Taiga» `docs/backlog/taiga-ids.json`, который коммитится рядом с карточками; запасной — тег `card-<ключ>` у US и поиск по фильтру `tags` (фильтра по `subject` в документации Taiga нет, на него не опираемся).
7. Сообщает итог: создано, пропущено, ошибки.

**Запасной вариант (б)**: `POST /api/v1/userstories/bulk_create` (doc-api `user-stories/bulk-create.adoc`): `project_id`, `bulk_stories` (заголовки, по одному на строку), необязательный `status_id`; остальное заполняется вручную по шаблону. Применять, если карточек получается меньше 100 (рекомендация Q-28).

**Оценка** хранится кастомным атрибутом «Оценка, ч» (число), а не `points`.

## 6. DoD (definition of done)

`CONTRIBUTING.md` в репозитории **отсутствует** (проверено), поэтому ссылаться пока не на что. По Q-08 процесс оформляет ментор: когда `CONTRIBUTING.md` появится, этот раздел заменяется ссылкой на него, а пункты ниже сверяются с ним (при расхождении прав `CONTRIBUTING.md`).

Известные решения Q-08 (ответ ментора): ветка `dev`; ветка `main` только у ментора; перекрёстное ревью учеников обязательно; PR как можно меньше строк (числового лимита нет); тесты не пишем, но `app.component.spec.ts` и `vitest` не удаляем. Не названы: squash или merge, язык коммитов, API-тесты агента — **решает ментор**.

Временный DoD карточки (до `CONTRIBUTING.md`):
- [ ] Все пункты «Приёмки» карточки пройдены вручную на сид-данных `DEMO` и записаны в PR («Дано / Действие / Ожидаю → результат»).
- [ ] Под `eva_viewer` проверено, что недоступное скрыто (если карточка касается действий).
