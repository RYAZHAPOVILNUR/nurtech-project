# ТЗ бэкенда MVP: общие соглашения

Относится ко всем пакетам ТЗ MVP. Продукт описан в [01](../01-scope.md), [04–07](../04-board.md); модель и права — в [08](../08-data-model-and-permissions.md). Контракт — [openapi/openapi.yaml](openapi/openapi.yaml) (`info.version` 0.1.0).

Это урезанная версия полного ТЗ из `docs/backend/`. Пути, имена полей и `operationId` совпадают с полным контрактом 0.7.0, лишние поля и ручки убраны (список отличий — [openapi/CHANGELOG.md](openapi/CHANGELOG.md)). Когда MVP будет готов, проект пойдёт к полной версии по `docs/`.

**Кто главнее при расхождении.** Пути, поля, коды ошибок и лимиты — OpenAPI. Роли и ключи прав — [08](../08-data-model-and-permissions.md), раздел 4. Поведение бэкенда — пакеты ТЗ 01–04. Если нашли расхождение, сообщите ментору.

**Что обязательно.** Только **контракт** (OpenAPI) и **наблюдаемое поведение**: что клиент получает в ответ и что потом видят пользователи. Критерии приёмки проверяются через API, без доступа к коду. Технологии, СУБД, схему хранения, блокировки, алгоритмы, логи и тесты выбирает разработчик бэкенда; разделы «Рекомендации (необязательно)» можно не выполнять.

| № | Пакет | Документ | Нужен фронту к неделе |
|---|---|---|---|
| 1 | Вход, сессия, приглашение, профиль, проекты, права, участники, справочники, шаблоны | [01-auth-projects.md](01-auth-projects.md) | 0 (каркас ментора) |
| 2 | Задачи: создание, поля, теги, подзадачи, история, поиск, связи, ссылки | [02-tasks.md](02-tasks.md) | 1 |
| 3 | Доска: карточки по колонкам, перенос и порядок | [03-board-and-move.md](03-board-and-move.md) | 2 |
| 4 | Комментарии и списания времени | [04-comments-worklogs.md](04-comments-worklogs.md) | 4 |

Недели — ориентир, а не обязательство ([02-plan.md](../02-plan.md)). Пока пакета нет, фронт работает на константах, типизированных по OpenAPI.

**Служебные средства (вне контракта).** Пользователей, проекты, членство и ссылки-приглашения заводит разработчик бэкенда: консольными командами, скриптом или сидом, на свой выбор. Ручек администрирования в MVP нет. Минимальный набор команд:
- создать пользователя (имя) и выдать ссылку-приглашение `APP_BASE_URL/invite/<token>` (одноразовая, 7 дней);
- выдать новую ссылку существующему пользователю (если он забыл пароль): прежний пароль и прежние ссылки перестают работать, логин сохраняется;
- создать проект (название, ключ, шаблон `dev` | `simple`), при необходимости — доску-фильтр (например, «Frontend» с фильтром по направлению);
- добавить пользователя в проект с ролью `owner` | `admin` | `member` | `viewer`; в проект добавляют только тех, кто уже принял приглашение (у них есть логин).

## 2. Протокол
- Базовый путь `/api`, JSON (`Content-Type: application/json`), UTF-8.
- Идентификаторы — строки UUID. У задачи есть читаемый ключ `PROJ-123`.
- Моменты времени — ISO 8601 в UTC (`2026-11-03T10:15:00Z`). Даты без времени (срок, дата списания) — `YYYY-MM-DD`. Длительности — целое число минут. «Сегодня» на бэкенде — дата по UTC.
- Поля JSON — `camelCase`; значения перечислений, коды ошибок и причины в `fields` — `snake_case`.
- Пустые необязательные значения в ответах — `null`, а не отсутствие поля. Необязательная строка, пришедшая пустой или из пробелов, сохраняется как `null`.
- **`null` в запросах:** в `POST` `null` равен отсутствию поля; в `PATCH` отсутствие поля — «не менять», `null` — «очистить» (только у очищаемых полей, у остальных — 422 `invalid`).
- Строки в теле перед проверкой длины обрезаются по краям (`trim`); пустое обязательное поле — 422 `required`.

## 3. Ошибки
Единый формат тела при 4xx и 5xx:
```json
{ "error": { "code": "validation_failed", "message": "Проверьте поля формы", "fields": { "title": "too_long" } } }
```
- `code` — стабильная строка из перечня `ErrorCode`; `message` — текст на русском для показа пользователю;
- `fields` — только при 422 и 409 `name_taken`: ключ — имя поля запроса, значение — причина из `FieldErrorReason`;
- `requestId` — только в теле 5xx.

Фронт реагирует по **HTTP-статусу**, а не по коду ([03-ui-rules.md](../03-ui-rules.md), раздел 8). Поэтому `message` у 409 должен быть понятен пользователю без доработки на фронте («Такая связь уже есть», «Связь создаст цикл блокировок», «Карточку успели переместить, доска обновлена»).

| HTTP | Когда | `code` |
|---|---|---|
| 400 | неверный формат запроса, нет `Content-Type: application/json` у не-GET с телом | `bad_request` |
| 401 | нет сессии; неверный логин или пароль | `unauthenticated`, `invalid_credentials` |
| 403 | нет права; не прошла проверка `Origin` | `forbidden` |
| 404 | не найдено или нет доступа; недействительное приглашение | `not_found`, `invitation_invalid` |
| 409 | конфликт состояния | `username_taken`, `name_taken`, `link_exists`, `link_cycle`, `stale_position` |
| 422 | не прошла валидация | `validation_failed` |
| 429 | превышен лимит попыток (заголовок `Retry-After`) | `too_many_attempts` |
| 5xx | ошибка сервера | `internal_error` |

**Нарушение схемы → причина в `fields`:** нет обязательного поля или пусто после `trim` — `required`; `maxLength` — `too_long`; `maxItems` — `too_many`; повтор в массиве — `duplicate`; `enum`, `format`, неверный тип, `null` у неочищаемого поля, поле, которого нет в схеме запроса, — `invalid`. Остальные причины (`taken`, `not_found`, `not_member`, `not_allowed`, `reason_required`, `same_task`, `in_future`) описаны в операциях.

**Какой id — какая ошибка.** Идентификатор в пути (или не UUID в пути) не найден — 404 `not_found`. Идентификатор в теле, которого нет в проекте, — 422 (`fields.<поле> = not_found`); пользователь, который не участник проекта, — `not_member`. Исключения: значения фильтров доски (раздел 5) и соседи в `move` ([03](03-board-and-move.md)).

**Пароль.** Короче 8 символов или без буквы или цифры — 422 (`fields.<поле> = invalid`); длиннее 128 — `too_long`.

Сообщения не раскрывают лишнего: при входе всегда `invalid_credentials`, без уточнения, неверен логин или пароль.

## 4. Сессия и права
- Сессия — httpOnly cookie `sid`; все ручки, кроме публичных (`x-public: true`), требуют сессии, иначе 401.
- У каждой ручки в OpenAPI `x-permission: <ключ>` или `none` (достаточно сессии); то же написано в `description`.
- **Порядок ответов в ручках проекта.** Проект берётся из пути (`/projects/:projectId/...`) или из ресурса в пути (`/tasks/:taskId`, `/boards/:boardId`, `/comments/:commentId`, `/worklogs/:worklogId`). Порядок: нет сессии — 401; проект или ресурс не найден, либо пользователь не участник проекта — 404 (существование не раскрывается); у роли нет ключа — 403; проверка «своё» и прочие правила ручки — 403 или 422/409.
- Права считаются по текущему членству на каждый запрос: смена роли действует на следующем же запросе.

## 5. Списки и фильтры
- Пагинация только у комментариев (курсор `before` + `limit`, ответ `{ items, hasMore, nextCursor }`). Остальные списки отдаются целиком.
- `q` — не длиннее 100 символов, иначе 422 (`fields.q = too_long`); после `trim` пустой `q` — фильтра нет.
- Списки значений в query передаются через запятую; повтор значения не ошибка (дубли отбрасываются); больше 50 значений — 422 (`too_many`).
- **Неизвестный идентификатор в фильтре доски.** Проверяется формат, а не существование: значение не UUID (и не `me` / `none`, где они допустимы) — 422 (`fields.<параметр> = invalid`); корректный UUID, которого нет в проекте, отбрасывается, а если значений не осталось, фильтр не применяется. Так не ломаются закладки со старым фильтром.
- **Курсор** `before` — непрозрачная строка из `nextCursor` предыдущего ответа. Удаление записи, на которой остановилась выдача, не ломает «Показать ещё»: выдача продолжается без пропусков и повторов. Строка, которая не разбирается, — 422 (`fields.before = invalid`).

## 6. Безопасность
- Cookie `sid`: `HttpOnly`, `SameSite=Lax`, `Secure` в продакшене, `Path=/`.
- Для не-GET запросов проверяется `Origin` (или `Referer`) по списку `ALLOWED_ORIGINS`; нет ни того ни другого — 403 `forbidden`.
- Во всех ответах `Referrer-Policy: no-referrer` (токен приглашения лежит в адресе страницы).
- Фронт и `/api` открываются с одного origin. CORS — только для origin из конфигурации, `credentials: true`. В разработке `ALLOWED_ORIGINS` включает `http://localhost:4200`.
- Пароли, хеши и токены сессий в ответах не возвращаются. Токен приглашения неугадываем и показывается один раз (в ссылке).
- Каждый ответ содержит `X-Request-Id` (присланный клиентом или новый); в теле 5xx то же значение в `error.requestId`; стек и текст исключения в ответ не попадают.
- `DEV_SEED=true` в продакшене запрещён: приложение не стартует.

## 7. Конфигурация
Видимое снаружи поведение задают: `APP_BASE_URL` (для ссылок-приглашений), `ALLOWED_ORIGINS`, `SESSION_TTL_DAYS` (по умолчанию 7), `INVITATION_TTL_DAYS` (по умолчанию 7), `DEV_SEED`, `DEV_SEED_PASSWORD` (без значения по умолчанию). Остальное (хранилище, логи, порт) — на выбор разработчика.

## 8. Контракт и данные для разработки
- Ответы соответствуют `openapi.yaml`: пути, поля, обязательность, форматы, статусы, коды ошибок.
- У каждой операции есть уникальный `operationId` (глагол + сущность: `createTask`, `moveTask`) — из него фронт получает имена методов клиента. Ответы 400 и 500 объявлены у каждой операции.
- **Источник истины** — `docs-short/backend/openapi/openapi.yaml` в репозитории фронта. Изменение контракта — PR с повышением minor в `info.version` и строкой в [CHANGELOG](openapi/CHANGELOG.md); бэкенд не меняет контракт «по месту».
- **Тестовые данные.** `DEV_SEED=true` создаёт пользователей, проекты и задачи из разделов «Тестовые данные» пакетов (пароль у всех — `DEV_SEED_PASSWORD`); повторный старт не создаёт дублей.

## 9. Инварианты и одновременные запросы
Эти правила клиент видит всегда; ни один запрос и ни одна пара одновременных запросов их не нарушает.
- Номер задачи уникален в проекте, идёт по возрастанию и не переиспользуется.
- Имя тега уникально в проекте без учёта регистра; логин уникален.
- Между двумя задачами не больше одной связи `blocks` в одном направлении; цикла `blocks` нет.
- Порядок карточек внутри статуса однозначен: две карточки не занимают одну позицию, два чтения подряд отдают один порядок.
- Приглашение одноразовое.

Если два одновременных запроса по отдельности допустимы, а вместе нарушили бы инвариант, один успешен, второй получает ответ из таблицы (не 500):

| Ситуация | Второй запрос получает |
|---|---|
| Создание двух задач в одном проекте | 201 с другим номером |
| Создание двух тегов с одним именем | 409 `name_taken` |
| Две связи `blocks`, замыкающие цикл (A→B и B→A) | 409 `link_cycle` |
| Перенос двух карточек в одну позицию | 200 или 409 `stale_position`; общих позиций нет |
| Два `accept` одного приглашения | 404 `invitation_invalid` |

**Критерий приёмки.** Скрипт отправляет такую пару одновременно 20 раз: ни одного 5xx, ни одного второго успеха там, где в таблице ошибка, ни одного нарушенного инварианта (проверяется последующими `GET`).

## 10. Сквозное поведение
| Поведение | Что видит клиент |
|---|---|
| Смена статуса задачи (только `move`) | `statusId`, позиция, `updatedAt`, событие истории `status`; в колонке категории done задача видна `doneWindowDays` дней от момента закрытия |
| История | все изменения одного запроса имеют общий `createdAt`; события не удаляются |
| `updatedAt` задачи | обновляется при изменении полей, тегов, статуса, связей, ссылок, комментариев; не обновляется списаниями и перестановкой внутри колонки |
| Списки и вложенные данные | всё нужное экрану приходит в одном ответе: исполнители, теги, родители, `blocked` в карточках доски; связи, ссылки, подзадачи, суммы в `TaskDetail`. Клиенту не нужен запрос на каждый элемент |

**Повторы.** Ключа идемпотентности нет; фронт блокирует кнопку на время запроса. `PATCH` с теми же значениями — 200, событий истории нет. `move` в тот же статус и ту же позицию — 200, `reason` игнорируется. Повторный `DELETE` — 404. Повторный `POST` создания — ещё один объект (кроме уникальных: 409 `name_taken`, `link_exists`, `username_taken`).

**Критерии приёмки.**
1. Каждый ответ содержит `X-Request-Id` и `Referrer-Policy: no-referrer`; в теле 5xx `error.requestId` равен заголовку.
2. Тело любого 4xx и 5xx — `ErrorResponse` с `code` из перечня.
3. Не-GET без `Origin` и `Referer` — 403; не-GET с телом без `Content-Type: application/json` — 400.
4. `dueDate` и `date` отдаются строкой `YYYY-MM-DD`.

## 11. Рекомендации (необязательно)
- **СУБД.** PostgreSQL ≥ 14; скрипт сброса и пересоздания базы для разработки.
- **Пароли и токены.** argon2id (или bcrypt с cost ≥ 12). Токены приглашений и сессий хранить хешем, генерировать криптостойко, минимум 128 бит.
- **Логи.** Структурные (JSON), с `X-Request-Id`; пароли, токены и cookie не логировать, токен в адресе `/invitations/<token>` маскировать. Swagger UI на `/api/docs` вне продакшена.
- **Конкурентность.** Номер задачи — атомарным `UPDATE … SET taskSeq = taskSeq + 1 RETURNING`; цикл связей — под advisory-блокировкой проекта; расчёт позиции карточки — под блокировкой строки статуса. Нарушение уникального ограничения при гонке превращать в 409 с кодом, а не в 500.
- **Без N+1.** Исполнителей, теги, суммы времени и счётчики подгружать пакетно: число SQL-запросов на запрос API не зависит от числа элементов.
- **Курсор.** base64url от пары (`createdAt`, `id`).
- **Индексы.** Ориентир — полная модель, `docs/13-data-model-and-permissions.md`, раздел 7.
